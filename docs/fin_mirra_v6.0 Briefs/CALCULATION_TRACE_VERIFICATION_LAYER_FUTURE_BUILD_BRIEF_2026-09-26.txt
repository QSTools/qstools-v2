3. DESIGN DIRECTION (discussed, NOT yet decided/built)
===============================================================================
- Root: Business Modelling (the top of the chain, what a user actually
  looks at first).
- Branches downward through: Business Outcome (per-source labour/asset) ->
  Cost Allocation groups -> individual staff/assets -> P&L / Opening Hours
  inputs at the leaves.
- NOT a strict tree. Known shared/parallel connections that need explicit
  handling in the display, not just nested nodes:
    - one general-overhead pool feeding multiple working groups at once
    - an asset shared/co-deployed across multiple groups
    - a staff member split across multiple groups
  Design needs a way to show "this value is shared - see everywhere else
  it feeds" rather than assuming every branch is self-contained.
- Exact JSON shape and UI hierarchy component: NOT decided - settle once
  the existing page's current code is actually read (Section 1).

DESIGN FINDING, SESSION 14 CONTINUED (2026-09-27) - CONTRIBUTION MARGIN VS
  FULLY-LOADED COST (logged, not built - new lens, not a calc bug):
  Surfaced live-testing the two-staff overhead split (Paul $50/hr vs Junior
  $35/hr, equal hours). Owner's question: at what point is a lower-earning
  team member actually COSTING the business money, vs. simply carrying a
  smaller-but-still-positive contribution toward fixed overhead that would
  otherwise fall entirely on someone else?
  THE GAP: the page currently answers only ONE of two genuinely different
  questions -
    Q1 (shown today): does this source's revenue cover its FULLY-LOADED
      cost, including its allocated share of overhead? (net_profit =
      modelled_revenue - true_cost, true_cost includes overhead_share)
    Q2 (NOT shown, the one that actually matters for "am I quietly going
      out of business"): does this source's revenue at least cover its
      OWN DIRECT cost (wage only, no overhead)? If yes, removing that
      source would make the business WORSE off, not better, even if Q1
      is negative for them - because overhead is mostly fixed and would
      simply fall on whoever remains.
  This is the standard contribution-margin-vs-fully-allocated-cost
  distinction from cost accounting - a source can correctly show red on
  Q1 (fully-loaded) while still being a net positive on Q2 (contribution).
  The current page conflates the two, so a source flagged as "not paying
  its way" cannot currently be distinguished from "would make things
  worse if removed" vs. "would make things better if removed" - a real
  gap for the stated purpose of this tool (surfacing where a business is
  quietly losing money) and explicitly relevant to a future agent-driven
  "analyze where the business is leaking money" use case (this brief
  Section 4 - the same structured output built for a human audit trail
  is meant to serve an AI agent's analysis too).
  DATA ALREADY EXISTS, not yet surfaced as a comparison: each labour
  source's own direct cost is already its own node
  (cost_allocation.labour_type.<id>), separate from true_cost
  (which folds in the overhead share). No new calculation needed - this
  is a missing VIEW/comparison, not missing data.
  FUTURE BUILD: add a contribution-margin figure (revenue - direct cost
  only, overhead excluded) alongside the existing fully-loaded profit
  figure, so a source can be shown as e.g. "losing money fully-loaded,
  but still a net contributor - removing this source would increase,
  not decrease, the shortfall on everyone else" rather than just a flat
  red flag. Needs its own design/build session - not fixed inline.
