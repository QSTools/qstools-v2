2. WHY NOW, NOT LATER
===============================================================================
Building this as a byproduct of the verification work already underway
(rather than as a separate project after) means the module tracing already
being done by hand becomes the page's real content, instead of having to
re-derive it all again later. Explicit owner decision: build incrementally
as each module is verified, not as a single later push.

===============================================================================
3. DESIGN DIRECTION (discussed, NOT yet decided/built)
===============================================================================
- Root: Business Modelling (the top of the chain, what a user actually
  looks at first).
- Branches downward through: Business Outcome (per-source labour/asset) ->
  Cost Allocation groups -> individual staff/assets -> P&L / Opening Hours
  inputs at the leaves.
- NOT a strict tree. Known shared/parallel connections that need explicit
  handling in the display, not just nested nodes:
    - one general-overhead pool feeding multiple working groups at once
    - an asset shared/co-deployed across multiple groups
    - a staff member split across multiple groups
  Design needs a way to show "this value is shared - see everywhere else
  it feeds" rather than assuming every branch is self-contained.
- Exact JSON shape and UI hierarchy component: NOT decided - settle once
  the existing page's current code is actually read (Section 1).

===============================================================================
4. SECOND USE CASE - SAME INITIATIVE, NOT A SEPARATE ONE
===============================================================================
The same structured JSON output this page produces for human audit is also
exactly what an AI agent would need to answer "why is this number what it
is" without re-tracing the whole codebase each session. Treat this as one
build, not two - a byproduct of building the audit page properly, not an
extra scope item.

This is the same underlying idea as some existing summary modules (Model
Readiness, Recovery Summary, etc.) being considered for a future
JSON-for-reporting/agent layer - noted as a related but separate
observation, not to be conflated with rebuilding those modules now.
