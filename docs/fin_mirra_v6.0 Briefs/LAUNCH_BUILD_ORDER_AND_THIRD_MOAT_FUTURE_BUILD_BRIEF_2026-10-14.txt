2. FULL BUILD ORDER TO LAUNCH
===============================================================================
  1. Finish the asset smoke test (nearly done - see
     SMOKE_TEST_v6_0_BRIEF_2026-09-26.txt and the kickoff doc's current
     "NEXT STEP" state for exact position: OPEN-D, OPEN-E, asset-pricing
     hard block, idle cost into net profit, S1).

  2. Build server-side "moat" plumbing. Prove it on ONE small, already-
     verified calculation before anything else relies on it. Do not migrate
     broadly until this one proof is live-tested and confirmed correct.

  3. Migrate calculation/selector files to the server. Whole files only,
     never split mid-logic (a calculation chain depends on exact order within
     a file; splitting risks silently changing behaviour). Entry point: a
     thin dispatcher/registry (app/api/calculate/route.js + a lookup table),
     not one API route per calculation. The dispatcher does no calculation
     logic itself and stays inside the ~600-line file convention.
     VERIFIED 2026-10-14 (see moat brief Addendum 1, A3): every calculation
     hook today is "use client" and imports lib/calculations/*.js directly;
     no API route touches the calculation chain yet. This step has not
     started.

  4. Build units through the tool fully, BEFORE launch - not coming-soon,
     not gated. Reasoning: units will likely require shared-calculation-file
     changes; making those changes after a live client database exists
     risks corrupting or tangling both live numbers and stored history at
     once (unacceptable risk with real client financial data, per the
     owner's own prior experience with messy personal databases). Accepted
     this may add ~6 months to the timeline.

  5. Add the database. Stores monthly Xero-imported P&L/balance sheet
     history, modelled vs. actual over time. This is the core switching-cost
     moat (Addendum 1, A2/A7 layer 1) and the hard prerequisite for 5b below.

  5b. Build the aggregation/benchmark module once the database is live and
      holds real rows. Self-contained, outside the existing calculation
      chain, reads only finished output-contract data (per_source, capacity
      coverage gap, overhead_per_hour, stream shares, required_recovery_rate,
      revenue, industry/trade - all already exist, see Addendum 1 A8). New
      pieces only: consent flag, size-band bucket, the aggregation query
      itself. Sample-size floor: ~20-30 businesses per category x size-band
      for directional signal (Addendum 1, A9) - construction is the leading
      first-trade candidate.
      HARD GATE BEFORE THIS STEP SHIPS ANYTHING USER-FACING: a lawyer reviews
      the actual design (band width, sample floor, update cadence, exact UI
      copy) for price-signaling exposure and signs off. See moat brief
      Addendum 1, A11 (RealPage / Agri Stats precedent). Design direction
      already leaning toward: bands not numbers, historical/monthly not live,
      never a recommended rate. Not cleared yet.

  6. Stress test against the SERVER-MIGRATED version (not pre-migration) -
     this both proves migration integrity and tests a new failure mode
     (server load from many businesses computing simultaneously, vs today's
     per-browser compute). Current test dataset: ~2 productive staff, 1
     non-productive. Plan to scale to 10 / 100 / 1,000 staff/assets up to a
     ~$100M business. For other trades (window cleaner, mechanic, etc.):
     build deliberately-shaped synthetic data with a known-correct answer to
     check against, rather than hunting for real external P&Ls.

  7. Launch.
