2A. DESIGN RULES SET BY THE OWNER 2026-10-16 (database and agent)
===============================================================================
  - The database is built and live before anyone real uses the tool. There is
    no localStorage-to-database migration for launch.
  - One database for all users (multi-tenant). A user seeing another
    business's data must not be possible: row-level isolation from day one.
  - Every calculated number the tool produces, at every level, is stored in
    the database, written by the same calculation code the app uses.
  - The agent only explains stored numbers. It does not calculate. A clearly
    labelled what-if is the one possible exception, and is proposed to run
    through Business Modelling's own lever calculation.
  - Order of work: stress test, then database, then concurrency/load testing.
    Load testing is background work and not a launch blocker.
  - NOT decided: which fields get field-level encryption beyond the baseline
    (TLS, at-rest, row-level security); database host; what "every level"
    means in rows. See the 2026-10-16 stress test brief Sections 5 and 11.

A4. DATABASE SCOPE DECISIONS (owner) - resolves stress test brief Q-3 and Q-6
-------------------------------------------------------------------------------
  Three layers:
    BASELINE         dimensions: staff, assets, groups, rates, settings.
    LIVE             time-stamped facts: P&L and Balance Sheet imports now; purchase orders and timekeeping later.
                     Reference baseline records by ID.
    STORED OUTPUTS   every calculated figure.
  "Every level" means EVERY SINGLE CALCULATION NODE, not only each module's output contract. Reason (owner): the
  explainer agent can then answer any question about any number in the business, which is the point of building it.
  Adding purchase orders and timekeeping later is additive to the LIVE layer. It does not touch the baseline or the
  calculation code.
  To reconcile at schema time: stress brief 5.3 proposed a MODELLED layer (Business Modelling scenarios). The 1b
  scratch overlay decides whether scenarios are stored at all.

  HARD RULE: one shared multi-tenant database with row-level tenant isolation. Cross-business data leakage must be
  structurally impossible. Not one database per business.

  Two tests that must pass before launch (they go in the stress and load test section, run after R6):
    (a) Performance of full-node storage at about 1,000 businesses: write volume and query speed, measured. Not a
        generic "handles requests".
    (b) An active attempt to breach tenant isolation: query as one business and confirm no row of another is
        reachable. Do not assume row-level security works.

  ENCRYPTION. Baseline (in transit, at rest, row-level isolation) is settled and non-negotiable. A further
  field-level layer is NOT decided. It costs queryability for the fields it covers, so it needs a concrete field
  list. Starting position, offered as advice and explicitly not final: personally identifying fields (staff names,
  contact details, possibly pay tied to a named person) are the strongest candidates; operational and calculated
  figures (group costs, recovery rates) rely on the baseline plus isolation, because Cost Allocation and Rate Builder
  sum and query them in bulk. The owner agreed the list goes to someone experienced in securing financial SaaS data
  BEFORE the schema is finalised at R6.

  HOSTING: deferred by the owner. No provider is chosen. Verify at-rest encryption and recovery for whichever is.

A5. CHANGING CALCULATIONS OR STORAGE AFTER REAL DATA EXISTS
-------------------------------------------------------------------------------
  Owner concern, from experience (Power Query, replacing values by hand): a late change to a calculation or to
  storage tangles the data until the database has to be wiped and rebuilt. Protections already in the design,
  recorded here in one place: additive, versioned migrations; a backup before every change; one source of truth (a
  stored number is always written by the same calculation code the app uses, never hand-patched or re-derived
  elsewhere); a field's meaning changes only across full releases; every change must pass the synthetic-data
  regression suite before it can reach the real database; and because every node is stored, a wrong number can be
  traced to the node where it diverged. None of this makes a live system risk-free. It removes the specific
  wipe-and-restart failure mode. Detail: REGRESSION_HEALTH_CHECK_SUITE brief.
