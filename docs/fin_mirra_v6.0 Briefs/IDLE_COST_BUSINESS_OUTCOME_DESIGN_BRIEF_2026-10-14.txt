1. KEY FINDING - NET PROFIT ALREADY CARRIES IDLE COST
===============================================================================
Nothing needs adding to any net profit calculation. Doing so would count the cost twice.

Evidence (hooks/useBusinessOutcomePerSourceRevenue.js):
  - get_group_covered_hours (L274): an asset-driven group's covered hours = MIN(seat hours, sum of assigned labour hours).
  - build_labour_sources: revenue_hours = covered hours x the staff type's share of labour hours (L348-359), so labour
    revenue is capped at covered hours.
  - The same rows carry direct_cost = the FULL assigned_cost (L361) and true_cost = direct_cost + overhead_share (L388).
  - So when assigned labour hours exceed the asset hours, the extra hours cost money and earn nothing. That loss is
    already inside the working group's net profit (BO-6, 2026-09-23).
  - Matches Addendum 8 (2026-10-07): with Paul and Jack in one unit, group modelled revenue = $150 x 1,414 covered hours.
A labour SHORTFALL reaches net profit the same way (revenue capped at covered hours, via BO-6).

What IS missing is VISIBILITY, not arithmetic:
  1. idle_labour_hours / idle_labour_cost / idle_labour_warning exist only on the Cost Allocation group cost row
     (costAllocationGroupCostBuilder.js L189-215) and show only as a Cost Allocation notice. Business Outcome never
     reads them. The rows reach Business Outcome unmodified (useCostAllocation.js passes operational_group_cost_rows
     through), so the fields are already available there.
  2. Business Outcome's Capacity Coverage Gap dollar value only exists when get_group_blended_rate finds a GROUP-level
     calculator. That function skips every asset-linked calculator (L63-65). A group priced per asset (the current model since
     Path B) therefore shows NO dollar figure for either shortfall or surplus.

2. OWNER DECISIONS (2026-10-14, by discussion)
===============================================================================
D-IDLE-1  RATE: idle hours are valued at RAW LABOUR COST per assigned hour = assigned_labour_cost / assigned_labour_hours.
          Not the blended rate. This is the figure Cost Allocation already holds as idle_labour_cost.
  Reasoning agreed: the labour cost is already INSIDE the blended rate, so showing both would count the same hours twice.
  Idle hours are paid wages with no billable job, not a missed sale, so the honest loss is the wage. The figure equals the
  net profit the idle hours cost. Worked example used: 200 idle hours x $40 = $8,000 (blended $90 x 200 = $18,000 rejected).

D-IDLE-2  GATING (new idle line): the Business Outcome idle display respects the per-working-group tick box
          "The labour in this working unit is tied to the asset only" (labour_tied_to_asset). Ticked = shown.
          Not ticked = no idle flag. Each working group is judged on its own tick box, the same rule Cost Allocation applies.
  Reasoning agreed: an unticked group's labour can flex to other work, so a surplus there (for example two operators on one
  machine) is not a proven loss. Accepted trade-off: a real idle problem stays unflagged until someone ticks the box.

D-IDLE-3  GATING (existing surplus displays) - settles former open item O-1. The existing "Overstaffed" (wasted_cost) row in the
          Capacity Coverage Gap table is gated on the SAME per-working-group tick box as the new idle line. The matching
          "things to check" paragraph for wasted_cost (BusinessOutcomeTruthSituationSummary.jsx L588-593) follows the same rule.
  Reasoning (owner): both idle displays must agree and not show a confusing number when the box is not ticked.
  Note: the gap table's surplus figure (|asset hours - labour hours| x labour cost per hour) is the same quantity as
  idle_labour_cost when the box is ticked, so after gating the two displays agree by construction.

D-IDLE-4  CM-9b BASIS - settles former open item O-3. The Rate Builder labour panel divides by the group's ASSIGNED labour
          hours, not by the capped recovery hours, so surplus labour can no longer inflate a displayed rate. Business Outcome's
          labour mix (calculate_labour_mix_charge_rate = sum(rate x assigned hours) / sum(assigned hours)) stays as it is; the panel
          is brought into line with it.
  Reasoning (owner): "we can't have an inflated number". Worked example: one operator at $150/hr, 2,000 assigned hours, machine
  needs 1,000: dividing by recovery hours shows $300/hr; dividing by assigned hours shows $150/hr.
  Scope of the change (from code): lib/calculations/rateBuilderLabourByStaffType.js, build_labour_staff_type_breakdown,
  share = assigned_hours / hours_basis (L67), where hours_basis is the recovery hours passed in. Both charge_rate and floor_rate
  use that share. It changes the result ONLY for groups whose assigned labour hours differ from recovery hours (surplus labour, and
  manual_hours groups in either direction); a single staff type with assigned hours equal to recovery hours is unchanged.
  Consequence to be aware of: the panel then shows an hours-weighted AVERAGE rate. A deliberate two-person crew on one machine
  will no longer show both rates added together. This is the same crew-versus-idle question as O-4 and is accepted.
  Calc map: CM-9b closes; update calc map s8 (panel labour) and s12 (CM-9 NOTE UPDATE 2026-10-13) in the same commit.

Kept separate (agreed): asset capacity that goes unbilled because labour is SHORT is the existing shortfall line ("Revenue
not earned"). It is a different measure, valued as revenue, and may fire on the same group as idle. Never combined into one number.

4. O-2 - SHORTFALL DOLLARS FOR GROUPS PRICED PER ASSET (investigated, method awaiting sign-off)
===============================================================================
OWNER DIRECTION (2026-10-14): shortfall stays valued as revenue not earned (the blended, labour-plus-asset basis), not at labour cost.
  The open problem is only that a per-asset-priced group has no single group rate to read.
FINDING: there is no need to invent or combine a blended rate. For a per-asset group the model ALREADY leaves out a definite amount
  of revenue, and it can be computed from the same functions Business Outcome uses:
    asset part   = sum over the group's assets of  asset calculator rate x asset hours x (1 - MIN(1, covered hours / required_asset_hours))
                   (get_asset_revenue_hours with full coverage, minus with actual coverage)
    labour part  = labour mix charge-out rate x shortfall hours       (calculate_labour_mix_charge_rate; shortfall = required_asset_hours - assigned labour hours)
    shortfall $  = asset part + labour part
  This is exactly the revenue BO-6 removes, so it reconciles to net profit by construction.
  Legacy group-calculator groups keep gap hours x group blended rate (unchanged). The same identity holds there (labour + asset inside the rate).
EDGE CASES to decide at sign-off:
  E-1 An assigned staff type with no saved charge-out rate makes the labour mix understate (a missing rate counts as 0). Proposal: show the hours
      and mark the dollar figure "not fully priced" instead of a low number (same no-fallback principle as OPEN-E).
  E-2 An asset with no calculator lines has no rate (the row already says "Not priced"). Same proposal: hours shown, dollars marked incomplete.
  E-3 A group with NO labour assigned has no staff type to value the labour part. Show the asset part and say the labour part cannot be valued.
Why not "combine the calculators into one blended rate": the machine calculators price the machine only (Stage 1b), so a combined rate is
  asset rates weighted by hours plus a labour mix, which is the same sum as above but would add a second place that defines a group rate.
