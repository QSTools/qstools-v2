1. WHY V6.0 EXISTS - READ THIS FIRST
===============================================================================

Business Modelling has stalled. It cannot be trusted until the calculation
chain beneath it is proven correct end to end, starting from Cost
Allocation.

The dependency chain is:

    P&L / Labour / Assets  -->  COST ALLOCATION  -->  Rate Builder
        --> Business Outcome  -->  Business Modelling

Cost Allocation is the hinge. Everything upstream of it just feeds it.
Everything downstream of it (Rate Builder, Business Outcome, Business
Modelling) depends entirely on trusting what it distributes. This pass
exists to verify Cost Allocation is doing exactly what it's supposed to
do - so that everything built on top of it can finally be trusted.

v5.x briefs were written before live-data injection points and Business
Modelling's wiring into Business Outcome existed. Rather than patch old
assumptions, v6.0 starts the verification chain fresh from page one.

DEFINITION OF DONE for this pass: not "every brief is tidy" - done means
any number Business Modelling needs can be traced and trusted, from its
real source through to Cost Allocation's output.

A known, explicitly parked gap to watch throughout: the business_type (labour_based vs.
product_based) setting (set on the intro page) is NOT fully
wired through every downstream module yet. As each module is verified,
explicitly note whether it correctly respects this setting or silently
assumes one. Do not fix this inline unless trivial - log it, keep moving,
fix as a dedicated pass once the gaps are fully known.

A SECOND parked item, added 2026-09-23 during the Business Outcome 8b
session: an owner-remuneration setting (payroll / shareholder salary /
drawings) surfaced while reconciling the P&L cost-gap against Labour's
figures. Logged for a future Labour + Reconciliation session - see the

4. PROCESS RULES FOR EVERY V6.0 SESSION
===============================================================================

Full detail: "Working_Conventions - PowerShell Patching, CSS, and Numeric
Verification" (repo root) - this section is a summary, that document is
authoritative.

- One module per chat session. Do not carry v6.0 work for multiple
  modules in one long conversation. (Note: the 8b follow-up session was
  treated as a continuation of the same Business Outcome module, not a new
  module, and was completed the same day as the core pass - this is
  consistent with the rule, since it is still one module.)
- Project knowledge for each session holds ONLY: this kickoff document,
  the variable tracker, the file map, and the ONE module brief currently
  being worked. Nothing else. Swap the module brief out before starting
  the next module's session.
- View the actual current file content fresh before patching - never
  patch against context from earlier in the conversation or an earlier
  session.
- All edits via PowerShell, Apply-Patch (IndexOf/Substring), UTF-8-no-BOM
  I/O. Never Set-Content for writing code.
- Require an explicit "Patched:" / "NOT FOUND:" / "AMBIGUOUS" confirmation
  for every patch. A passing build does not confirm a patch landed. NOTE
  (8b): a NOT FOUND result can also mean a CRLF/LF mismatch in the patch
  script's own string comparison, not necessarily a real content mismatch -
  normalize line endings before comparing, then re-check the file directly
  if a patch unexpectedly fails to match.
- Build after every batch of patches.
- Live-test against real (or deliberately-padded-and-documented) data
  before trusting a fix, not just a clean build.
- Watch for the two recurring bug classes: (a) a standalone function
  outside a hook can't see hook-local variables - pass explicitly as
  parameters; (b) a storage/selector layer that explicitly rebuilds an
  object rather than spreading silently drops unlisted fields (this is
  exactly the bug class Section 5's file-map notes exist to catch -
  see BUSINESS_OUTCOME_FILE_MAP_v6_0.txt Section 4, "the selector
  explicitly lists every field it returns"). Both are now checkable with
  a script before assuming a manual trace is needed - see Section 5:
  check_field_parity.py for (b)-style field drops, check_has_loaded_guard.py
  for the has_loaded race condition.
- NEW (8b): before changing what a shared hook reads or returns, grep for
  EVERY caller of that hook, not just the one you're trying to fix - a hook
  can be called from more than one place (on-page component, an output-
  contract composer, even from INSIDE another core calculation hook). Check
  what each caller actually reads from the return value before assuming a
  change is safe; a narrower dependency than it first appears (e.g. only
  two of a hook's many fields are actually consumed by a given caller) can
  turn an apparent circular-dependency blocker into a safe, scoped change.
- Numbers in living reference docs (file map, variable tracker): NOT
  ALLOWED. These describe mechanism, not current state - they must stay
  true regardless of what data is loaded. Numbers belong only in dated,
  point-in-time records (a module's [VERIFIED 2026-xx-xx] brief entry),
  clearly tied to what they proved, so they read as historical evidence
  rather than a claim about today's data.
- Confirm git status before any commit.

5. TOOLING AVAILABLE (run locally, paste summary back - saves tokens)
===============================================================================

Location: D:\QSTools\qstools-web\Py\audit-scripts\
  - find_inline_css.py           - inline style={{}} / style="" sweep
  - find_duplicate_css.py        - duplicate CSS rule-block finder
  - find_field_references.py     - find every file/line referencing a
                                    given field name (use this to check
                                    whether a field survives the hook ->
                                    selector -> component chain before
                                    assuming it's broken)
  - check_field_parity.py        - compares a hook's returned fields
                                    against its selector's returned
                                    fields, flags anything dropped
                                    (bug class (b) below). Usage:
                                    check_field_parity.py <hook_file>
                                    <selector_file>
  - check_has_loaded_guard.py    - scans the repo for hooks that write
                                    to localStorage inside a useEffect
                                    and flags any missing a has_loaded
                                    guard (Section 4 rule on race
                                    conditions)

Run from repo root (D:\QSTools\qstools-web), e.g.:
    python Py\audit-scripts\find_field_references.py group_overhead_share

Paste the terminal summary back, not the full .txt report, unless more
detail is specifically needed.

WHEN TO RUN EACH (do not run any of these "just in case" - only when the
trigger below actually applies, to avoid wasted token spend reviewing
irrelevant output):

  - find_field_references.py - run when verifying a specific module in
    Phase 2, to confirm a field genuinely exists (or doesn't) across the
    hook/selector/component chain BEFORE spending tokens tracing it by
    reading files manually. Also useful (8b) for finding every CALLER of a
    hook, not just every reader of a field - a simple grep across the repo
    (not limited to this script) served the same purpose in 8b when the
    question was "who else calls this hook", not "who reads this field".

  - check_field_parity.py - run once per hook/selector pair, at the
    point that pair's module is actually reached in Phase 2. Not useful
    before then - there's nothing yet to compare.

  - check_has_loaded_guard.py - optional, repo-wide, no specific module
    dependency. Can be run once early (e.g. during Phase 0/1 setup) to
    seed the variable tracker's Section 8 with a baseline gap list, OR
    deferred and run once during/after Phase 2 Step 4 (Assets - the
    module most likely to touch localStorage-heavy hooks). Either
    timing is fine; running it twice with no code changes in between is
    the only thing to avoid.

  - find_inline_css.py / find_duplicate_css.py - DO NOT run during
    Phase 1/2. These belong to the separate CSS Consolidation brief
    (Section 7), which starts only after v6.0 verification is complete.
    Running them now produces a report that will be stale by the time
    that brief actually starts.
