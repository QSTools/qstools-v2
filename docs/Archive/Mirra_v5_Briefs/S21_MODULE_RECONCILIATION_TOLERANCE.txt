# 1. PURPOSE

Module Reconciliation used to treat every variance the same way: one
number, one tolerance, one "is this ok or not" judgement per check.
This brief exists to fix that, because it doesn't match how the
underlying numbers actually behave.

This brief was produced from a voice-dictated design conversation, then
built and corrected against the real codebase in the same session. Not
everything in the original design survived contact with the real data
model - those corrections are documented inline below rather than
hidden.

# 2. CORE PREMISE

100% reconciliation to the P&L will never happen and is not the goal.
Perfect reconciliation is a myth even in properly run finance teams.

The real design question Module Reconciliation needs to answer is not
"does this balance to zero" but:

"Is this variance close enough to trust, or is it actually a problem
hiding in the numbers?"

Those are two different questions and need two different answers per
check, not one blended variance percentage.

# 3. TIMING GAPS VS DATA ERRORS - THE CENTRAL DISTINCTION

Every variance Module Reconciliation surfaces falls into one of two
fundamentally different categories.

## 3.1 Timing gap

Definition: the module's number is the true, correct cost. The P&L
simply has not caught up to it yet, because of when the accountant
journals things.

Examples: ACC and KiwiSaver not yet journaled by the accountant, asset
finance interest journal not yet posted, end-of-year journal not
posted at all.

Correct system behaviour: tell the user to trust the module, not the
P&L. Do not present this as a variance the user needs to close or
resolve.

## 3.2 Genuine data error

Definition: something was actually entered wrong or left out. The two
numbers should reconcile closely, and if they don't, the data is
wrong.

Example already found in this project: the trial-staff bug, where a
staff member was missing from Labour and the numbers diverged for a
real reason, not a timing reason.

Correct system behaviour: no lenient tolerance. Flag it, mean it, point
the user at what to check.

# 4. DIRECTION OF VARIANCE MATTERS

- Module HIGHER than P&L: the module is capturing a real cost that the
  P&L hasn't recorded yet. Generally the more legitimate, lower-concern
  situation - the normal shape of a timing gap.
- Module LOWER than P&L: the model may be undercooking something.
  Deserves more scrutiny than the reverse case.

This is implemented directly in buildVarianceCheck's timing_aware
logic: only module_amount > source_amount can ever produce
timing_expected. Module lower than P&L always gets the normal warning
treatment, even on a timing_aware check.

# 5. WHAT WAS ACTUALLY BUILT

## 5.1 timing_expected classification (buildVarianceCheck)

A check marked timing_aware: true now classifies a material variance
as timing_expected (not a warning) when module_amount is higher than
source_amount. is_warning is false in that case, so it does not count
toward the Warnings pill and does not push module_reconciliation_status
toward review_required.

Wording used: "{module} is ahead of its P&L benchmark. This is
expected if the accountant hasn't journaled it yet - trust {module},
not the P&L, for this figure."

## 5.2 Dollar-floor tolerance fallback

Percentage tolerance breaks down when the P&L benchmark (denominator)
is small or zero - a fully-explained timing gap can read as a 100%+
variance. When timing_aware is on and source_amount is below a
configured low_denominator_threshold, materiality is judged against a
flat dollar tolerance instead of variance_percent.

Applied to:
- asset_finance_variance: threshold $500, floor tolerance $250
- labour_on_costs_variance: threshold $300, floor tolerance $150

Both pairs are placeholder values, not yet tuned against a broad data
set across multiple businesses. Safe to adjust without touching the
classification logic itself (both are named constants in
reconciliationRules.js).

## 5.3 Labour wages/on-costs split

Two new checks: labour_wages_variance (tight tolerance, no timing
leniency - genuine data errors only) and labour_on_costs_variance
(timing_aware, same dollar-floor treatment as Asset Finance).

CORRECTION FROM ORIGINAL DRAFT: the original design assumed a P&L
labour-lines split might require a P&L module change (new
classification field per line). It did not. Investigation found:

- P&L side: pnl_output_contract.labour_lines already exists as an
  array of individual lines, each with a line_name and amount,
  returned straight from lib\calculations\profitAndLossCalculations.js
  with no selector filtering in between. Split by name pattern - the
  same technique the codebase already used for is_interest_line
  (matching "interest" in a line_name). On-cost line_name patterns:
  "acc", "kiwisaver", "kiwi saver", "esct", "levy", "on-cost",
  "on cost". Everything else in labour_lines counts as wages.
- Module side: labourOutputContractSelectors.js already exposes
  total_employer_contribution_annual (on-costs total, summed across
  active staff via sum_staff_value). Wages is simply
  total_labour_cost_annual minus that figure - no new Labour
  aggregate was needed either.

No changes were made to the Labour module itself. This was purely a
reconciliation-layer change once the real field names were confirmed
against the live codebase (not assumed from the brief).

## 5.4 General Overheads - no change

Confirmed no change needed, per the original design conversation.
getGeneralOverheadsVarianceCheck is untouched.

# 6. IMPLEMENTATION NOTE - DEAD CALCULATION FOUND AND FIXED

While wiring the Labour page to display real reconciliation data, a
pre-existing, unrelated bug was found and fixed:
lib\selectors\labour\labourStatusSelectors.js contained its own
independent Labour-vs-P&L variance calculation
(get_labour_reconciliation), called from useLabour.js with a
hardcoded pnl_benchmark_total of 0. Since the benchmark was always
zero, this silently reported "green"/"Ready" on the live Labour page
regardless of the real numbers - a live bug affecting real users, not
a design choice.

This calculation has been removed entirely. buildLabourStatus now
covers only Labour's own completeness (staff name, hours, rate,
productivity, positive costs) - not P&L variance. There is now exactly
one place in the codebase that calculates Labour-vs-P&L variance:
lib\reconciliation\reconciliationRules.js, consumed via
useModuleReconciliation. This directly closes the "two calculations
that can silently drift apart" risk that prompted this investigation.

# 7. IMPLEMENTATION NOTE - PER-EMPLOYEE VS WHOLE-BUSINESS

An initial attempt wired useModuleReconciliation directly into the
Labour page and displayed labour_benchmark_total /
total_labour_cost_annual on the per-employee LabourCompactWorkspaceCard
review tab. This was wrong even with correct numbers: those figures
are whole-business totals across all staff, and the card is scoped to
one employee's profile - showing a whole-business variance next to one
staff member's name misrepresents what the number means.

Corrected: the per-employee card no longer shows any P&L comparison.
It shows only per-employee readiness (profile, staff, labour class,
productive hours, warnings) plus a link to the Module Reconciliation
page, where the real whole-business comparison lives.

# 8. IMPLEMENTATION NOTE - UI HIERARCHY

Initial build showed labour_variance, labour_wages_variance, and
labour_on_costs_variance as three flat sibling cards on the Module
Reconciliation page. This misrepresented the relationship - wages and
on-costs are components of the blended Labour figure, not independent
comparisons.

Corrected: app\module-reconciliation\page.jsx attaches
labour_wages_variance and labour_on_costs_variance as a sub_checks
array on the labour_variance check object, rather than including them
in the top-level component_checks list.
ModuleReconciliationSummaryCard.jsx's ComponentRow was refactored to
take lifted state (open_check_ids, hovered_check_id, toggle_check)
instead of pre-bound per-row handlers, so it can render itself
recursively for sub_checks - indented, same click/hover/expand
behaviour as a top-level row, no duplicate "Go to Labour" button (the
parent's already covers it). The Warnings pill count and its
auto-expand-on-click behaviour were both updated to walk into
sub_checks, so the count still reflects every real warning (including
nested ones).

# 9. RELATIONSHIP TO S20 (MANUAL ACCEPT / BASELINE)

S20 (S20_MODULE_RECONCILIATION_ACCEPTED_VARIANCE_BASELINE_BRIEF_v5_0)
proposed a manual "Accept" button / baseline-snapshot mechanism so a
user could mark a known variance as acknowledged.

S21 partially supersedes that need, but does not fully replace it:

- For the timing-prone checks (Asset Finance interest, Labour
  on-costs), S21's automatic timing_expected classification removes
  the need for a manual accept action entirely - the system already
  knows these are expected lags and says so without requiring a click.
- Manual accept per S20 still has a role for genuine one-off
  exceptions that don't fit a known pattern - cases the system cannot
  classify automatically.
- S20 has not yet been rebuilt to reflect this narrower scope. It
  still exists only as a chat-delivered draft, not saved into this
  repo's docs\Mirra_v5_Briefs folder. Recommended next step: rescope
  S20 to cover only the residual manual-accept cases before building
  any of it, so it isn't built as a general-purpose button across
  every check when S21 already covers the majority of what it was
  going to solve.
