# 1. WHY THIS BRIEF EXISTS

Revenue Summary (`/revenue-summary`) was reviewed for a layout-only UX cleanup.

That review found the page's real problem is not layout. It is purpose.

Revenue Summary currently asks the user to manually retype Sales Revenue,
Material Cost, Operating Expenses, Subcontract Costs, and Equipment Hire —
figures that already exist properly in Revenue / COGS and the P&L. This
creates a second, manually-typed, easily-out-of-sync copy of numbers the
system already owns elsewhere.

The one genuinely useful thing Revenue Summary does — comparing what the
P&L says against what the cost modules calculate (Labour Variance) — is
not a new idea. It is a smaller, less rigorous, hand-rolled version of a
system that already exists: Module Reconciliation.

Module Reconciliation (`hooks/useModuleReconciliation.js`,
`lib/reconciliation/moduleReconciliation.js`,
`lib/reconciliation/reconciliationRules.js`) is already implemented and
already feeds Model Readiness's checks. It already pulls P&L benchmark
figures (labour_benchmark_total, assets_benchmark_total,
general_overheads_benchmark_total, asset_finance_benchmark_total) and
module-calculated figures (total_labour_cost_annual,
total_asset_cost_annual, total_general_overheads) into one object. It has
no dedicated page and its variance checking is currently a single lumped
comparison, not the per-module breakdown its own controlling brief (10)
specifies.

Decision: retire Revenue Summary as a manual-entry page, and complete
Module Reconciliation into the real "P&L vs modules, and why" page the
user actually needs.

# PART B — EXTEND MODULE RECONCILIATION WITH PER-MODULE VARIANCE

# B1. CURRENT STATE (CONFIRMED FROM CODE)

`reconciliationRules.js` currently produces these checks:

- module_ready_checks: binary pass/fail for P&L, Labour, General
  Overheads readiness
- assets_readiness_check: binary pass/fail
- employee_overheads_check: binary — flags legacy employee_overheads
  still present in P&L
- legacy_running_cost_check: binary warning — flags legacy
  running_cost_annual on Assets
- business_cost_variance_check: ONE lumped variance — compares
  module_total_business_costs (labour + assets + overheads combined)
  against setup_module_benchmark_total (or full P&L benchmark if the
  setup-module benchmark is zero). Has variance_amount and
  variance_percent. Flags "fail" if variance_percent > 1%.

All the raw inputs needed for a per-module breakdown already exist in
`normalised_reconciliation_inputs`:

- labour_benchmark_total vs total_labour_cost_annual
- assets_benchmark_total (and asset_finance_benchmark_total) vs
  total_asset_cost_annual (and total_asset_interest_annual)
- general_overheads_benchmark_total vs total_general_overheads

Nothing currently compares these pairs individually. This is the gap.

# B2. WHAT TO ADD

Per controlling brief 10, sections 18-20, add three new check-builder
functions to `reconciliationRules.js`, following the same shape as the
existing `getBusinessCostVarianceCheck`:

1. getLabourVarianceCheck
   - source_amount = labour_benchmark_total
   - module_amount = total_labour_cost_annual
   - variance_amount = module_amount - source_amount
   - variance_percent = abs(variance_amount) / source_amount * 100
     (guard divide-by-zero)
   - severity: warning if variance_percent exceeds an agreed threshold,
     not auto-blocking (brief 10 section 18: "Do not call variance an
     error automatically")
   - possible_reasons: fixed list per brief 10 section 18 — timing
     difference, payroll classification difference, owner/director pay
     treatment, employee overheads included elsewhere, missing staff,
     P&L period mismatch, module uses forward/current cost while P&L is
     historical

2. getAssetFinanceVarianceCheck
   - source_amount = asset_finance_benchmark_total
   - module_amount = total_asset_interest_annual
   - same variance shape
   - possible_reasons per brief 10 section 19 — end-of-year journal not
     posted, loan interest timing, principal/interest split issue, asset
     finance classified elsewhere, asset not entered

3. getGeneralOverheadsVarianceCheck
   - source_amount = general_overheads_benchmark_total
   - module_amount = total_general_overheads
   - same variance shape
   - possible_reasons per brief 10 section 20 — asset finance excluded,
     running costs transferred to Assets, staff overheads reclassified,
     COGS accidentally included in overheads, manual overhead
     adjustment, operating expense classification issue

Each new check gets added to the `reconciliation_checks` array alongside
the existing ones. The existing lumped `business_cost_variance_check` is
kept as-is (it remains useful as the overall combined figure) — these
three are additive, not a replacement.

# B3. WHAT MUST NOT CHANGE

- No changes to Labour, Assets, General Overheads, or P&L source
  calculations.
- No changes to Cost Summary, Business Summary, or any other downstream
  consumer's own math.
- No auto-correction of variance. Reconciliation shows the gap; it does
  not resolve it.
- No new blocking behaviour unless explicitly agreed — per brief 10,
  variance is evidence, not automatically an error.

# PART C — BUILD THE MODULE RECONCILIATION PAGE

# C1. ROUTE

New route: `/module-reconciliation`

Sidebar placement: needs confirmation — likely under "Business Truth"
alongside where Revenue Summary previously sat, since it plays a similar
role in the flow (P&L period truth-check before Business Summary).

# C2. UI STRUCTURE (per brief 10 section 37)

1. Module Reconciliation Status Strip — overall status, warning count,
   blocking count, trust state
2. P&L Benchmark Summary — P&L period, revenue, COGS, operating expense
   benchmark, net profit, other income
3. Module Totals Summary — Labour, Assets, General Overheads, Cost
   Summary total cost burden
4. Reconciliation Checks Table — all checks including the three new
   per-module variance checks, each showing source amount, module
   amount, variance amount, variance percent
5. Variance Explanation Panel — for each variance check with a non-zero
   material variance, show the possible_reasons list from B2
6. Blocking Checks Panel
7. Warning Checks Panel
8. Help Panel

This is a read-only page. No inputs. All figures are pulled from
existing module output_contracts via `useModuleReconciliation`.

# C3. ACCEPTANCE CRITERIA

- Page builds clean (npm run build)
- All three new per-module variance checks display source amount,
  module amount, variance amount, variance percent, and possible-reason
  list when variance is material
- No source module values changed
- No downstream module (Model Readiness, Business Summary, etc.) breaks
- Old Revenue Summary route no longer in sidebar; files preserved, not
  deleted
- Visual verification via screenshot before commit
- git status clean after commit, with commit message documenting scope
