## 1. What Business Modelling actually is

/business-modelling answers "what happens if I change a rate, a markup, or a cost?" - a what-if tool, built on top of Business Outcome's real, live, already-verified per-source data. It is NOT a separate calculation engine with its own independent numbers - it reuses Business Outcome's real calculation chain, feeding it modelled (hypothetical) inputs instead of just displaying real ones. This "reuse the engine, don't rebuild it" principle is the core architecture decision governing everything on this page.

## 2. How Outcome feeds Modelling - the real handoff, confirmed working

The chain: `useBusinessOutcomePerSourceRevenue()` (hooks/) → `selectBusinessOutcomePerSourceRevenue()` (lib/selectors/business-outcome/businessOutcomePerSourceRevenueSelectors.js) produces `per_source` → `useBusinessModelling()` (hooks/) calls this and exposes `per_source` itself (added 2026-09-14, was previously computed internally but never returned - needed for the scenario redesign below) → `lib/selectors/businessModellingLeverSelectors.js`'s `buildLiveLeverHeadline(per_source, rate_target_by_group_id, materials_markup_percent)` is the real live-lever engine, consuming `per_source` directly and applying whatever rate/markup changes are currently set.

This handoff is real, live, and already confirmed working correctly - do not re-investigate whether it works, only what it reads (Section 4 below is the one open question).

## 3. What's built and shipped - don't re-verify from scratch

**The live-lever card** (`BusinessModellingLeverCard.jsx`, always visible at the top of the page): per-group rate targets, materials markup target, real-time resulting net profit, breakeven rate per group, proportional suggestions. Reads `per_source` directly via the chain above. This IS Business Modelling's real engine - has been for some time, confirmed via commit history (`f98b9f3`, "S31 Phase 2-3").

**Business Modelling Scenario Redesign - Baseline/Upside/Downside** (built 2026-09-14, see BUSINESS_MODELLING_SCENARIO_REDESIGN_DECISION_LOCK_2026-09-12.txt, same folder as this doc, for the full original decision):
- **Baseline**: NOT editable. A real, locked, dated snapshot of "where the business actually is right now" - built via `buildBaselineSnapshotFromLive(per_source)` (lib/calculations/businessModellingScenarioCalculations.js), which calls `buildLiveLeverHeadline` with EMPTY levers (`{}`, `null`) so it captures genuine reality, never a half-edited scenario. Full history kept (never deleted, exactly one `is_current`), stored via lib/storage/businessModellingScenarioStorage.js (key `qs_tools_business_modelling_scenario_state_v1`, separate from the old system's key). Re-locking is suggested (not automatic), with manual revert always available.
- **Upside**: A single (not multiple) saved target scenario, using the live-lever engine's real levers. Computed via `buildUpsideHeadline(per_source, upside_scenario)` - deliberately uses the SAVED levers, not whatever's currently live-editable in the UI.
- **Downside**: Calculated live as breakeven, NEVER stored, via `calculateDownsideAsBreakeven(baseline_snapshot)`. If Baseline is profitable, Downside sits below it (room to fall); if a loss, above it (climb needed).
- UI: `components/business-modelling/BusinessModellingScenarioSection.jsx`, wired into the page below the existing live-lever card.
- Hook: `hooks/useBusinessModellingScenario.js` - takes `per_source` as an input (does not recompute it), has a `has_loaded` guard applied proactively (learned from an earlier session's race-condition bug elsewhere).
- **Real bug found and fixed during build**: Downside initially always showed "Lock a Baseline first" even with a real baseline locked - `calculateDownsideAsBreakeven` was checking a `baseline_snapshot.available` flag that does NOT survive the storage round-trip (the storage layer's `normaliseBaselineSnapshot` explicitly rebuilds the snapshot object listing only its 4 real data fields, silently dropping `available` - the same "middle layer drops the field" bug class this whole project has hit repeatedly). Fixed by checking the real underlying data (`total_net_profit`, `breakeven_revenue` both finite) directly instead.
- Live-verified with real data: Baseline locked at $630,568 net profit, Downside correctly showed $1,869,432 breakeven with the right distance message, a real lever change (Site Crew rate $75→$80/hr) saved as Upside correctly showed $712,618, genuinely different from Baseline.

**Old system** (`lib/storage/businessModellingStorage.js`, `lib/calculations/businessModellingCalculations.js`, rendered collapsed as "Previous scenario tools" on the page): deliberately left untouched as a safety net until the new system is fully trusted. Not yet retired - that's a separate, deliberate future decision, not something to do casually.

## 4. THE ONE GENUINELY OPEN QUESTION - pick up here

**Should Business Modelling's lever engine (and by extension, the new Baseline/Upside/Downside system) read View B's real materials markup instead of View A's residual figure?**

Confirmed facts:
- `buildBreakevenSummary` (lib/selectors/businessModellingLeverSelectors.js) is confirmed **View-A only** - reads `per_source.real_capacity` and `per_source.materials` (View A's residual construction: `total_revenue - labour_modelled - asset_modelled`), and does NOT read `per_source.view_b` at all.
- View B's materials figure is **real, stored, and independently anchored**: `total_cogs × (1 + markup%)`, using a real user-set 15% markup (`lib/storage/rateBuilderMaterialsMarkupStorage.js`, key `qstools_rate_builder_materials_markup_v1`). This is NOT a test value - it was confirmed as a deliberate real figure (previously a 10% test value, since updated).
- An earlier session's own resolution (session brief Section 3.2) states "View A is the trusted base for all lever math, View B's role is a check-and-balance overlay for the materials lever specifically, not a modelling input" - but this was decided BEFORE the real 15% markup existed as stored data, and a later reconciliation document (S32, 2026-09-08) explicitly flagged this as worth re-deciding now that real View B data exists, calling View B "the more honest architecture" without ever getting a final confirmed decision.
- Both the existing live-lever card AND the new Baseline/Upside/Downside system inherit whatever decision is made here, since both ultimately call `buildLiveLeverHeadline`, which calls `buildBreakevenSummary`.

**This is a real architecture decision, not a bug to fix.** Recommended approach for a new chat: pull real numbers for View A's residual materials figure vs. View B's real 15%-markup figure, using live data, show the actual gap to the user, and get an explicit decision before changing any code - same discipline used for every other architecture decision this project has made (see the depreciation-in-true-cost decision in FIXED_ASSET_REGISTER_IMPORT_SCOPING_BRIEF_2026-09-12.txt as a template for how that conversation went).
