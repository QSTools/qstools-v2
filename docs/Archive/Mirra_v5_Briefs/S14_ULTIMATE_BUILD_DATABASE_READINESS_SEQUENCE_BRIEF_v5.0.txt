# 1. PURPOSE

This brief records the future QS Tools / Mirra build sequence required before the system moves from browser/local state into a persistent multi-user database, historical reporting layer, dashboard intelligence layer, and embedded AI system.

It exists to prevent another major realignment.

It must be carried forward into the Pro migration.

This is not a feature build brief.

This is a future architecture control brief.

# 3. CORE CONTROL PRINCIPLE

The permanent database must not be built by directly transferring current browser/localStorage state into tables.

The database must only be designed after the business system has been aligned across:

- business questions
- required outputs
- required measures and dimensions
- current variables
- missing variables
- stable identities
- module ownership
- Business Outcome outputs
- Modelling inputs and outputs
- baseline, actual, target and scenario states
- historical reconstruction
- reporting facts and dimensions
- Dashboard data contract
- AI structured context
- calculation versions
- contract versions
- source lineage
- reconciliation requirements

---

# 4. LOCKED BUILD SEQUENCE

The future build sequence is:

1. Business questions
2. Required outputs
3. Required measures and dimensions
4. Variable audit
5. Ownership assignment
6. Missing-variable alignment
7. Output-contract lock
8. Application database entity design
9. Historical reporting schema design
10. Historical reconstruction proof
11. Downstream integration proof
12. Schema lock
13. Implementation

This sequence must not be reversed.

---

# 5. WHY THIS MATTERS

If the sequence is reversed, QS Tools risks:

- missing persistent fields
- unstable identities
- duplicated calculation logic
- repeated module realignment
- broken historical reconstruction
- weak Dashboard contracts
- incomplete AI context
- overbuilt database tables
- underbuilt reporting facts
- expensive migrations
- future schema redesign

The purpose of the sequence is to make later development additive rather than structural.

---

# 6. THREE-LAYER DATA ARCHITECTURE

QS Tools must support three connected but separate layers.

## Layer 1 - Application Database

Stores the operational business state:

- tenants
- businesses
- users
- module inputs
- profiles
- effective-dated versions
- baseline versions
- actual operating versions
- target models
- scenarios
- identities
- classifications
- import records
- calculation and contract version references

This layer reconstructs the business.

## Layer 2 - Calculation and Structured Output Layer

Uses the QS Tools calculation engine to produce:

- current business outputs
- baseline outputs
- target outputs
- scenario outputs
- variances
- warnings
- calculation traces
- driver outputs
- structured AI context

This layer calculates business truth.

It is not the primary storage layer.

## Layer 3 - Historical Reporting Layer

Stores analytical facts and selected calculated outputs for:

- month reporting
- quarter reporting
- year reporting
- supplier analysis
- customer analysis
- revenue and COG analysis
- baseline versus actual
- actual versus target
- historical Dashboard drilldown
- historical AI comparison

This layer analyses history.

It is not the editable application database.

# 12. POST-LOCK CHANGE CONTROL

After schema lock, future changes should normally use:

- new optional fields
- new child tables
- new dimensions
- new fact tables
- new contract versions
- new calculation versions
- controlled indexes
- controlled lookup values

The first response to a new feature must not be redesigning the core schema.

Breaking changes require:

- impact assessment
- migration script
- compatibility plan
- test plan
- rollback plan
- version increment

---

# 13. BUSINESS OUTCOME CONTROL

Business Outcome is the current commercial truth of the business.

It combines:

- revenue
- COG
- cost burden
- recovery
- gross profit
- contribution
- deterministic drivers
- data-quality warnings

Business Outcome is not a scenario page.

Business Outcome must not manually enter totals or duplicate source-module formulas.

It must expose stable outputs for:

- Modelling
- Dashboard
- historical snapshots
- AI structured context
- reporting exports
- recommendation logic

---

# 14. BUSINESS MODELLING CONTROL

Business Modelling and Scenario Engine must distinguish:

- baseline
- current actual
- approved target
- working scenario
- saved scenario
- archived scenario

Scenario inputs must not overwrite actual data.

Scenario calculations must be deterministic.

AI may explain scenario results but must not calculate authoritative scenario outputs.

---

# 15. DASHBOARD CONTROL

Dashboard is the primary decision surface.

It must combine:

- current business state
- locked baseline
- approved target
- performance gap
- Business Outcome
- structural drilldown
- historical trends
- warnings
- embedded AI access

Dashboard does not own calculations.

Dashboard must not create Dashboard-only versions of core metrics.

---

# 16. AI CONTROL

AI is advisory.

AI may:

- explain verified facts
- explain deterministic comparisons
- interpret patterns
- recommend controlled actions
- communicate uncertainty
- summarise trade-offs

AI must not own:

- financial facts
- business calculations
- baseline approval
- target approval
- scenario calculations
- pricing changes
- employment decisions
- asset disposals
- accounting treatment

Material recommendations must include:

- direct recommendation
- business objective
- supporting evidence
- expected effect
- assumptions
- risk
- confidence
- proposed test or implementation step
- success measure
- review period
- rollback or stop condition where relevant

---

# 17. PRICING OPTIMISATION CONTROL

Pricing recommendations must not be based on margin alone.

The system must consider:

- cost recovery
- margin
- demand
- capacity
- quote conversion
- customer and offering mix
- historical response
- strategic importance
- uncertainty

Internal cost and margin data can show pricing pressure or headroom.

It does not prove price sensitivity.

Quote outcome and demand data are required for stronger pricing recommendations.

---

# 18. ASSET STRATEGY CONTROL

Asset scenario modelling must compare:

- ownership
- finance
- leasing
- sale
- replacement
- outsourcing
- employee allowance
- reimbursement
- fuel-card support
- mixed arrangements

The model must separate:

- cash released
- debt repaid
- accounting gain or loss
- recurring annual cost
- recurring profit effect
- productivity effect
- capacity effect
- risk and control

Capital released must not be treated as recurring profit.

---

- unproven Dashboard contract
- unproven AI context
- unclassified critical gaps
- missing migration strategy
