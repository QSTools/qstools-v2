PART 1 - COST ALLOCATION BUG FIX (fully committed, verified, closed)
===============================================================================

## THE BUG
`minimum_recoverable_rate_per_hour` was IDENTICAL across every operating
group (395.43 for all 7 groups), when it should have been different per
group (matching each group's real labour+asset+overhead mix).

## ROOT CAUSE (two compounding bugs)
File: hooks/cost-allocation/useCostAllocationGroupRecoveryRows.js

  1. get_group_asset_ids(group) / get_group_staff_ids(group) looked for
     asset/staff IDs EMBEDDED directly on the group object
     (group.asset_ids, group.required_staff_ids, etc.) - fields that never
     existed. Real linkage is via SEPARATE assignment records:
     labour_group_assignments / asset_group_assignments, each with its own
     group_id field, staff_type_id / labour_type_id (labour) or asset_id
     (asset), and is_active.
     FIX: rewrote both functions to accept the assignment arrays and filter
     by group_id, matching a.is_active !== false.

  2. The exported hook `useCostAllocationGroupRecoveryRows` never received
     or passed through labour_group_assignments/asset_group_assignments to
     the internal build_operational_group_recovery_rows function at all -
     silently dropping the data even after fix #1's functions could have
     used it. FIX: added both params to the hook's destructured signature,
     its internal useMemo call, and its dependency array.

  3. Even after 1+2, labour/asset rates INSIDE the recovery-rows
     calculation still didn't always match Cost Allocation's own proven-
     correct numbers (different staff-matching logic, e.g. stale ID names
     like "senior_operator_senior_staff" vs "senior_operator_staff").
     FINAL FIX (in hooks/useCostAllocation.js, not the recovery-rows file):
     after calculate_cost_allocation() runs, MERGE each
     operational_group_recovery_rows entry's labour/asset/overhead figures
     directly from the matching operational_group_cost_rows entry (by
     group_id) - guaranteeing the two can never diverge again, since one
     is now literally sourced from the other.

## FILES CHANGED
  - hooks/cost-allocation/useCostAllocationGroupRecoveryRows.js
  - hooks/useCostAllocation.js (the merge step, in the `calculated` useMemo)

## VERIFIED (hand-checked against Cost Allocation's own Group Cost Stacks
   screen, /cost-allocation page, "Group costs" tab):
     PC55: $83.44/hr   2inc Line: $71.28/hr   Site Crew: $65.89/hr
     Foreman: $87.21/hr   PC15: $6.23/hr   Senior Crew/Senoir poe: $0

## DEBUGGING TECHNIQUE USED (may be useful again)
Browser DevTools console + React fiber tree walk, since this app is
localStorage-driven with no global debug object for most data:
  1. Click an element in DevTools Elements tab (sets $0)
  2. `Object.keys($0).find(k => k.startsWith('__reactFiber$'))` gets the
     fiber key
  3. Walk `fiber.return` upward checking `fiber.memoizedProps` for the
     data you want
  4. Watch for Fast Refresh going stale - $0 goes invalid after any hot
     reload; must reselect the element in Elements tab and re-run.
  5. Avoid JSON.stringify on React props (circular refs / Next.js internal
     Promises throw) - walk the object manually instead, checking for
     `.then`, `.$$typeof`, `instanceof Node` to skip non-data values.

PART 5 - S26 (NOT YET BUILT): MATERIALS/COG AS A REAL PEER - CRITICAL PATH
===============================================================================

Full brief: docs/Mirra_v5_Briefs/Business Outcome/Business Outcome New
Additions/S26_-_MIRRA_MATERIALS_COG_TARGET_MARKUP_VARIANCE.txt (already
updated twice this session with revisions - read the WHOLE file, sections

## ONE-LINE SUMMARY OF THE DECISION
Build a NEW, parallel "Materials shares equally" cascade (View B) that
treats materials as a genuine third peer source alongside labour/asset
groups - WITHOUT touching the existing, hand-verified "Materials
protected" cascade (View A, today's live behavior) at all. Once View B is
built and verified, add a toggle between the two (matching the S25
pattern) - do not silently replace View A.

## THE TWO CRITICAL FUNCTIONS TO UNDERSTAND FIRST (hooks/useBusinessOutcomePerSourceRevenue.js)

  apply_revenue_ceiling(labour_sources, asset_sources, total_revenue_reference)
    Only ever sums labour_total + asset_total. Materials was never part of
    the ceiling check - it's defined afterward as the pure residual.

  apply_real_capacity(labour_sources, asset_sources, materials_naive_revenue,
    materials_true_cost)
    THE hand-verified cascade ("matched to the cent against a 200,000-step
    numerical simulation across seven scenarios, plus six exact boundary
    [cases]" - per its own code comment). Two-phase:
      shortfall = max(0, materials_true_cost - materials_naive_revenue)
      Phase 1 (outer, across groups): v0 = sum of every group's own
        positive naive_net_profit; phase1_absorbed = min(shortfall, v0);
        phase1_factor = phase1_absorbed / v0; every profitable group
        scaled down proportional to its OWN naive profit share.
      Phase 2 (inner, within each group, across its individual sources):
        same proportional logic one level down.
      Materials is then FLOORED: materials_final_revenue =
        max(materials_naive_revenue, materials_true_cost) - always ends
        up >= breakeven by construction. verdict is "being_carried"
        whenever shortfall > 0, even though the number shown is floored
        at $0 (an earlier, separate fix this session, confirmed with user).

  CONFIRMED LIVE THIS SESSION: at real revenue, PC15 (currently the single
  most profitable group) absorbs the largest proportional share of any
  materials shortfall - not because of anything specific to PC15, purely
  because it currently has the largest positive naive_net_profit in the
  v0 pool.

## MATERIALS RESIDUAL CALCULATION (~line 676, hooks/useBusinessOutcomePerSourceRevenue.js)
  materials.revenue = total_revenue_reference - labour_modelled_revenue_total
                       - asset_modelled_revenue_total   (the residual)
  materials.true_cost = total_cogs + max(residual_overhead, 0)
  materials.net_profit = materials.revenue - materials.true_cost

## WHAT NEEDS TO CHANGE FOR VIEW B (per S26 Section 11/12)
  - materials needs its own modelled_revenue field = total_cogs * (1 +
    materials_markup_percent/100), using Part 2's Rate Builder markup
    number (readRateBuilderMaterialsMarkup())
  - materials needs to become a real "row" shaped like a labour_sources/
    asset_sources row (modelled_revenue, true_cost fields) so it can flow
    through NEW versions of apply_revenue_ceiling and apply_real_capacity
    as a genuine third array, not read afterward as leftover
  - Build these as NEW functions (e.g. apply_revenue_ceiling_v2,
    apply_real_capacity_v2 - exact naming TBD) alongside the existing
    ones - do NOT edit apply_revenue_ceiling or apply_real_capacity in
    place. The existing ones must keep working, untouched, indefinitely
    (or until a much later, separate, explicit decision to retire them).
  - UI: materials should get the same Current Rate vs Min Recoverable
    Rate pairing already shown for every operating group in Card 2 and
    the Cost Build-Up table - one more row in the same visual pattern,
    not a special separate card.

## 6.1 useRevenueCogs.js vs P&L as the source of COGS
useRevenueCogs.js (hooks/useRevenueCogs.js) is a real, separately-built
module (its own Xero-import step, plus supplier/invoice breakdown data
not currently displayed anywhere) that FOUR other real modules still
depend on: useBusinessOutcomeTruth.js, useBusinessSummary.js,
useRecoverySummary.js, useRevenueReality.js, plus the /revenue-cogs page
itself. It currently produces IDENTICAL COGS figures to P&L's Cost of
Sales total (confirmed by the user, since P&L's COGS is fed from the same
underlying Xero report). This session's Rate Builder markup feature
(Part 2) deliberately pulls from P&L directly instead, per explicit user
decision ("i dont need it for this section... we have everything we want
from the pnl in one import"). The larger question of whether
useRevenueCogs should be retired/consolidated into P&L entirely across
the WHOLE app (not just this one new feature) is still open and parked -
NOT decided, NOT started.

## 6.2 Business Outcome vs Business Modelling ~$20 discrepancy
Business Modelling maintains its OWN separate, independent calculation
engine rather than reading Business Outcome as its foundation and
re-running Outcome's cascade with edited inputs. This produces small
(~$20 on ~$1.84M revenue) but real discrepancies between the two pages'
net profit figures. Confirmed NOT caused by anything built this session -
pre-existing architecture. A genuine, larger architectural question, "not
yet written up as its own brief" as of this session's end.

## 6.3 Materials markup context panel (v4.0 brief concept, never built)
The OLD v4.0 Rate Builder brief mentions a "Material Markup Context
Panel" (blended material markup %, total COG, top COG categories by
spend) that was apparently planned once but never actually built -
confirmed via grep this session (blended_material_markup_context,
top_cog_categories, top_suppliers all return zero matches in the current
codebase). Not in scope for anything built this session; mentioned here
only because it surfaced during the search for existing materials-markup
infrastructure and might be relevant context for the S26 UI design.

PART 7 - GENERAL BUILD CONVENTIONS CONFIRMED/REINFORCED THIS SESSION
===============================================================================

  - PowerShell here-string ($@ ... @$) whole-block string matching is
    UNRELIABLE for this codebase - repeatedly failed due to invisible
    whitespace/line-ending differences between what Claude reconstructs
    from a prior view and the file's actual raw bytes. LINE-INDEX-BASED
    edits (Get-Content as an array, slice with 0-based indices, rebuild,
    Set-Content) are far more reliable - but ONLY when the exact line
    number is reconfirmed via a fresh Select-String or Get-Content call
    immediately before the edit, since every prior edit in the same file
    shifts subsequent line numbers.
  - After ANY multi-line insert or delete, immediately re-view the edited
    region before moving on - orphaned lines and duplicated closing
    braces from off-by-one mistakes happened repeatedly this session and
    caused real build errors each time. Cheap to catch immediately,
    expensive to trace later.
  - CSS: dedicated named classes only (e.g. business-outcome-modelled-tag,
    business-outcome-ledger-row) - never inline style={{...}} objects for
    anything matching an existing visual pattern. Check
    styles/modules/business-outcome.css FIRST for an existing class
    before inventing a new one. New table-shaped UI: CSS Grid row-classes
    (see Part 4's "convention 2.4" note), not real <table> elements.
  - Every new number surfaced in a UI this session was hand-verified
    against an independently-computed real figure BEFORE being trusted -
    this discipline caught the Part 1 bug and should continue,
    especially for anything touching apply_real_capacity (Part 5) given
    its own stated verification standard (200,000-step simulation).
  - Browser localStorage keys found this session, for reference:
      qs_tools_rate_builder_calculators_v1 - real, live, Rate Builder
        calculator lines (2inc Line Pump etc.)
      qs_tools_rate_builder_v1 - CONFIRMED ORPHANED, no code reads/writes
        it anymore (contained old "charge_models" data from a previous
        Rate Builder version)
      qstools_rate_builder_materials_markup_v1 - NEW this session, Part 2
      qstools_rate_builder_labour_source_rates_v1 - existing, unrelated
