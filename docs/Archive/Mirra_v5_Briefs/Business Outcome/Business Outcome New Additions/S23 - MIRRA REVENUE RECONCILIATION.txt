---

# 1. WHAT THIS IS

A new reconciliation line for Business Outcome: compare what total revenue
SHOULD be, built purely from things the business genuinely knows (real
operating group rates from Rate Builder, real hours, and Materials' real
entered markup), against what total revenue actually was, per the P&L.

This is a DIAGNOSTIC. It does not derive, assert, or replace any source's
"true" revenue. It flags a gap and lets the user investigate it.

---

# 2. WHY THIS EXISTS - THE PROBLEM IT SOLVES

Tonight's session spent significant time trying to find Materials' "current
markup" by subtracting labour/asset modelled revenue from total P&L revenue:

    materials_revenue = total_revenue - labour_modelled_revenue
                         - asset_modelled_revenue

This was confirmed, repeatedly and with hand-verified real numbers, to be
unreliable - not because of a coding error, but because it is structurally
incapable of isolating Materials. labour/asset "modelled revenue" is itself
a MODEL (real rate x real expected hours), not a measurement of what was
actually invoiced. Subtracting a model from a real total does not yield a
clean fact about the remainder - it silently absorbs whatever gap exists
between modelled and actually-billed labour/asset revenue, mixed in with
whatever Materials genuinely earned. No rearrangement of that subtraction
(pushing groups to breakeven, pushing them to full modelled revenue, or
anywhere between) changes this - confirmed algebraically and against real
data during this session.

The resolution reached tonight: Materials needs its OWN real, entered markup
assumption (see Section 6, dependency), the same way operating groups have a
real, entered rate in Rate Builder. Once Materials has that, a DIFFERENT and
much more useful comparison becomes possible - not deriving materials'
revenue from a subtraction, but PREDICTING total revenue from known
assumptions and checking it against reality.

---

# 3. THE CORE FORMULA

    predicted_total_revenue =
        SUM(group.current_rate_per_hour x group.recovery_hours)   [operating groups, real Rate Builder rates]
      + materials.cogs x (1 + materials.current_markup_percent)   [Materials, real entered markup]

    revenue_reconciliation_gap =
        real_total_revenue (P&L)  -  predicted_total_revenue

This is the same SHAPE as the cost reconciliation banner that already exists
in Business Outcome ("Real cost across every source: X vs. Y reported...
Variance: Z - see Cost Allocation for unassigned items") - just applied to
revenue instead of cost. It should sit alongside that banner, not replace it.

---

# 4. WORKED EXAMPLE (hand-verified this session)

Using real captured group data and the user's stated real materials markup
(10%):

    Labour/asset modelled revenue (5 groups, real rates x real hours):
        $1,210,572.00   [fixed - does not depend on total P&L revenue]

    Materials at 10% markup on real COGS ($1,240,090.70):
        $1,240,090.70 x 1.10 = $1,364,099.77

    predicted_total_revenue = $1,210,572.00 + $1,364,099.77
                             = $2,574,671.77

Tested against two real total-revenue figures from tonight's session:

    Against the $1,843,663 test figure (deliberately engineered to equal
    total_true_cost for cascade-testing purposes - NOT a real revenue
    figure):
        gap = $1,843,663.00 - $2,574,671.77 = -$731,008.77

    This large a gap is expected and correct - it confirms $1,843,663 was
    never meant to be consistent with real rates + real materials markup at
    the same time. It was a synthetic number for a different purpose. A gap
    this size against a REAL revenue figure would be a meaningful red flag;
    against a known-synthetic test figure it is not.

    Against the real $2,500,000 baseline:
        gap = $2,500,000.00 - $2,574,671.77 = -$74,671.77  (~3% of revenue)

    This is a small, plausible gap on a real figure - genuinely worth
    surfacing to the user as "here's where the model and reality don't
    quite line up," without claiming to know why. Possible real-world
    causes (not diagnosed by this feature, just consistent with a gap this
    size): some jobs priced below the stated 10% materials markup, some
    labour/asset hours not billed at full modelled rate, or a mix of both.

# 5. WHERE THIS LIVES

Business Outcome, as a new reconciliation banner alongside the existing cost
reconciliation banner. Suggested placement: directly below or beside
`ReconciliationBanner` (components/business-outcome-truth/
BusinessOutcomePerSourceRevenueCard.jsx, ~line 328), following the same
visual pattern (ok/warning status colour, plain-language variance
statement, link to the module that owns the discrepancy).

Suggested copy pattern (final wording TBC at build time):

    "Modelled revenue across every source: $X vs. $Y reported.
     Variance: $Z - built from your current rates and markups; a gap here
     means real pricing didn't fully match your rate/markup assumptions
     somewhere this period."

This is READ-ONLY / diagnostic. It does not feed into, adjust, or override
any other calculation on the page - specifically, it must NOT be used to
back-calculate Materials' "current markup" (that would silently reintroduce
the exact residual problem this brief exists to avoid - see Section 2).

# 6. DEPENDENCIES - MUST BE BUILT FIRST

This feature cannot be built until Materials has a real, entered markup
figure. It does not exist yet anywhere in the codebase, confirmed via
13_MIRRA_REVENUE_COGS Section 61 ("NO SALE VALUE ASSUMPTION" - the system
must not infer material sale value; unknown until user provides it) and via
Rate Builder's own brief (Section 24, material markup is currently only ever
shown as a BLENDED, DERIVED context figure - never a stored, entered one).

Required before this brief can be built:
  1. Materials gains a real, user-entered "current markup %" field
     (discussed and agreed this session - user's real figure is 10%,
     entered the same way Rate Builder holds an operating group's rate,
     not derived from any subtraction). This was scoped but NOT built
     during this session - it remains open.
  2. Confirm `group.current_rate_per_hour` genuinely reflects each group's
     real Rate Builder-entered rate (CONFIRMED this session for the 5
     existing operating groups - e.g. 2inc Line's current_rate_per_hour
     computes to $144.25/hr from real modelled_revenue / real hours, NOT
     the $71.29/hr cost-recovery figure shown elsewhere in Cost
     Allocation - these are two different, correctly-distinct numbers).
  3. Markup vs margin distinction must be resolved and visible wherever
     Materials' markup is entered/displayed (see S32 thread - Rate Builder
     gaining a margin field alongside markup, dual-display, live
     conversion). Confirmed this session: user enters markup (cost + X%),
     not margin - margin/GP% should show alongside as a read-only
     conversion, not a second independent input.
     Reference formulas (hand-verified this session):
         margin%  = markup% / (1 + markup%)
         markup%  = margin% / (1 - margin%)
     A working interactive reference model for these formulas already
     exists: Markup_vs_Margin_Playground.xlsx (built this session,
     zero formula errors, hand-verified against real materials COGS).

# 7. WHAT THIS DOES NOT DO (explicit non-goals)

  - Does NOT attempt to isolate or "solve for" Materials' true current
    revenue by subtraction. That approach was tested exhaustively this
    session (multiple engineered test-revenue scenarios, all hand-verified
    against real cascade code) and confirmed structurally incapable of
    producing a trustworthy result.
  - Does NOT replace or change the existing cost reconciliation banner -
    sits alongside it as a second, revenue-side check.
  - Does NOT feed Business Modelling's independent breakeven levers. Those
    remain correctly isolated per-source (S31 principle, reconfirmed this
    session as staying locked) - this reconciliation is Business Outcome
    diagnostic context only.
  - Does NOT attempt to explain WHY a gap exists (which jobs, which
    sources) - that level of detail requires the SOQ/Job/PO layer
    (referenced repeatedly this session as the eventual real fix for
    per-job, per-source actual data - not yet built).
