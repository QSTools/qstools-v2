# CFO Requirements Gap - Business Outcome (2026-09-12)

## Why this exists
Business Outcome is intended for eventual CFO adoption. This document is a scoping exercise, not a build brief: what standard CFO assessment tools/terminology already exist correctly on this page, what's real but unlabeled, and what's genuinely missing - with honest notes on whether the gap is a labeling fix, a build task, or blocked on data that doesn't exist yet. Written 2026-09-12 alongside the Health Gauge terminology work that triggered this review.

## IMPORTANT - live data context
Mirra is currently run session-by-session against manually-entered or single-snapshot-imported data (Labour, Assets, current Xero COGS pull). The Revenue/COGS module already imports 12 months of dated, per-supplier Xero data on each import - this is the one area with genuine historical depth today. Labour and Asset hours have NO dated/historical tracking - only current-state snapshots.

The user has confirmed two things are coming, not hypothetical:
1. [SHIPPED 2026-09-12] Balance sheet import from Xero - DONE, see Part 3 below for full detail. Currently Excel-file import (Xero trial/API access still pending), not yet a live API pull.
2. Live, ongoing data flow (not just periodic manual re-entry) - the system will eventually be fed continuously rather than snapshotted per session.

**Design implication: anything built against "the current snapshot" from here on should be built assuming it will later run against a live, updating feed, not a one-off import.** Where reasonably possible, calculations and any new UI should not hard-assume "this number was computed once and is now static" - prefer designs that would naturally re-compute correctly if the underlying data started updating more frequently, rather than baking in an implicit "annual snapshot" assumption that would need unpicking later. This is a design lens to apply going forward, not a mandate to rebuild anything that already works.

## Part 1B - Balance Sheet <-> Business Outcome connections (identified 2026-09-12, after shipping Balance Sheet)

Balance Sheet's 4 liquidity ratios were wired onto the Business Outcome page (2026-09-12) as a simple side-by-side display. That's not real integration - it's two independent data sources sitting near each other. Four genuine connections were identified, none built yet:

1. [SHIPPED 2026-09-12] **Current Year Earnings cross-check.** DONE - wired into BusinessOutcomeTruthSituationSummary.jsx's "Things to check" section, exact same severity-tiered pattern as the P&L cross-check. Live-tested against real data: immediately surfaced a genuine ~$284,000 discrepancy between Business Outcome's calculated net profit (+$184,475) and the imported Balance Sheet's Current Year Earnings (-$99,980) - exactly the kind of real signal this cross-check exists to catch. Also wired the 4 liquidity ratios directly onto the Business Outcome page (BalanceSheetRatiosCard, reused as-is). Balance Sheet's Equity section has a "Current Year Earnings" line, independently derived by Xero from the same underlying transactions Business Outcome's own net profit calculation uses. These two numbers should roughly agree. A mismatch is a genuine data-quality signal. This is the EXACT same pattern as the existing "P&L Net Profit cross-check" already built into the blurb (BusinessOutcomeTruthSituationSummary.jsx, severity-tiered drift, deferred to "Things to check") - same mechanism, different comparison pair. Low build risk because the pattern is proven and the data (Balance Sheet's totals.current_year_earnings-equivalent account, and Business Outcome's active_headline.total_net_profit) both already exist.

2. [SHIPPED 2026-09-12] **Fixed Assets reconciliation.** DONE - the original block (no aggregate purchase price, no depreciation tracking) was resolved without needing depreciation at all: calculateFixedAssetsReconciliation (lib/calculations/balanceSheetCalculations.js) detects whether the Balance Sheet separates gross value from depreciation as distinct account lines and, if so, sums only the gross lines - comparable to Assets' purchase_price without needing net-of-depreciation tracking on either side. If no depreciation split is found (a different business's Xero setup, net-only), safely returns net_only_cannot_compare rather than a false mismatch. Live-tested against real data: Balance Sheet gross Fixed Assets $242,755 vs Assets purchase price $629,000 - a genuine $386,245 gap, now visible in the blurb's Things to check. Also added: a new "Total Purchase Price" card on the Assets page itself (AssetTotalPurchasePriceCard.jsx) - purchase_price was previously stored per asset but never surfaced in aggregate anywhere, so the user had no way to audit this reconciliation's Assets-side number. Two real bugs found and fixed during build: (a) to_number() treated null as 0 instead of "not available" - would have silently reported a misleading reconciliation if Assets data was ever unavailable; (b) the new card initially used nonexistent name/label fields instead of the real asset_name field, showing "Asset 1/2/3" instead of real names - caught via live testing. Checked hooks/useAssets.js and lib/storage/assetStorage.js: purchase_price IS stored per asset (assetStorage.js) but is NEVER summed or surfaced anywhere in useAssets.js - no aggregate total currently exists. Worse: the Assets module has NO depreciation tracking at all. Balance Sheet's total_fixed_assets is explicitly net-of-depreciation (confirmed in the real test data - e.g. Motor Vehicles - Asset $140,480.87 + Motor Vehicles - Depreciation -$89,821.01 nets much lower). Comparing Assets' raw purchase_price sum against Balance Sheet's net figure would NOT be a real reconciliation - it would always disagree by roughly the depreciation amount, producing a misleading false-positive "mismatch" rather than a genuine data-quality signal. Two real prerequisites before this is buildable: (a) an aggregate purchase-price total actually surfaced from useAssets.js, (b) some depreciation tracking added to the Assets module. Do not build a naive version of this comparison - it would actively mislead rather than help.

FOLLOW-UP (2026-09-12, same day): the $386,245 gap most likely traces to Assets' purchase_price being manually-typed rather than sourced from real Xero data. A real Fixed Asset Register export was reviewed (29 real assets, with genuine per-asset purchase price, net book value, and accumulated depreciation) - this would let purchase_price be sourced from real data instead of guesses, and would also solve the depreciation gap noted above. Genuinely a major rejig, not a quick add - deferred and fully scoped separately, see FIXED_ASSET_REGISTER_IMPORT_SCOPING_BRIEF_2026-09-12.txt (same folder).

3. [SHIPPED 2026-09-12] **Liquidity as a constraint - standalone version.** DONE, without needing Business Modelling to exist. A real cross-check in the blurb: when a genuine "revenue_at_risk" capacity coverage gap exists (fixing it means adding real labour cost) AND working capital is negative, a plain-language paragraph connects the two - explains that the fix, while correct long-term, adds cost before the extra revenue becomes real, which could strain cash flow given the current liquidity position. Live-verified against real data (PC15 + -$54,035 working capital). The FULLER version (surfacing this as an actual constraint/warning INSIDE Business Modelling's lever UI, not just an observation in Business Outcome's blurb) still depends on Business Modelling existing - not yet built, tracked separately.

4. **Debt-to-equity as context for the scenario redesign (BUSINESS_MODELLING_SCENARIO_REDESIGN_DECISION_LOCK_2026-09-12.txt).** A highly-leveraged business might reasonably want more conservative Upside targets. Could surface as context/framing in the redesigned Baseline/Upside/Downside tool, not a hard constraint. Not yet scoped.

**Status: all four identified, none built.** Items 1 and 2 are cross-checks (display-only, low risk, proven pattern). Items 3 and 4 are genuinely harder - they'd change how Business Modelling behaves or is framed, not just what Business Outcome displays, and need their own design thought before building.

## Part 4 - Recommended order, if/when this becomes a build

Not a commitment, just a logical sequence given the dependencies above:

1. [DONE 2026-09-12] Balance sheet import - shipped, see Part 3.
2. Revenue/COGS trend view (fully buildable today, no blockers - lowest-risk place to start actual trend UI, and establishes the pattern the fuller trend view will later extend).
3. Labour/Asset historical tracking (a genuine data-model change - dated snapshots instead of current-state-only - needed before the fuller trended profitability view can exist. Likely comparable in size to the Asset Utilisation/Downtime prerequisite from the 2026-09-10/11 session - i.e. "a huge change in the system," not a quick add).
4. Full trended profitability view (revenue + labour + asset + materials, all periods) - depends on #3.
5. EBITDA-by-unit and formal segment reporting - depends on confirming per-source depreciation/amortisation/interest tracking exists or can be added; genuinely needs its own scoping session before any commitment on size.

## What this document is NOT
Not a commitment to build any of Part 3 or Part 4. Not a statement that the current page is CFO-inadequate - Part 1 shows real, correctly-built standard tools already exist. This is a scoping record so that when CFO-readiness work does happen, it starts from an accurate map instead of guessing what's missing.
