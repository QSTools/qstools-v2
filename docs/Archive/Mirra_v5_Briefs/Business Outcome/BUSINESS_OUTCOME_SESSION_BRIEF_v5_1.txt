## 3. View A vs View B - the full resolved picture (carried forward from 2026-09-10/11, still valid)

### 3.1 The mechanism
- View A's materials revenue is a residual: total_revenue - labour_modelled - asset_modelled. Forced by construction.
- View B's materials revenue is independent: total_cogs x (1 + markup%) - anchored to real COGS and Rate Builder's markup.
- Confirmed intentional, not a bug. Decision: keep View B's independent basis, do not force reconciliation.

### 3.2 Which view feeds Business Modelling - resolved
View A is the trusted base for all lever math. View B's role is a check-and-balance overlay for the materials lever specifically, not a modelling input.

### 3.3 Confirmed lever set for Business Modelling (five types, all View A)
1. Overhead cost change
2. Rate change
3. Labour cost/productivity change
4. Asset cost/utilisation change
5. Material markup sensitivity (View B's check-and-balance role attaches here)

### 3.4 Architecture principle - reuse the engine, don't rebuild it
Business Modelling should not have its own copy of the calculation chain. A lever input runs back through Business Outcome's SAME chain via a "calculation context" input bundle - real data fills it normally, Modelling fills an identically-shaped bundle with modelled values, same functions run against either. True size unknown until scoped against actual code - a next-session, at-the-computer task. Not yet scoped.

## 4. Lessons learned - worth remembering (accumulated across all sessions)

- The blurb has two separate prop lists that must stay in sync (Card JSX call, wrapper destructuring, wrapper's forwarding call into build_situation_summary). Miss the middle step and the paragraph silently doesn't render.
- Field-name traps: per_source.labour_groups[]/asset_groups[] use .group_modelled_revenue/.group_true_cost, NOT .modelled_revenue/.total_cost. per_source.materials uses .revenue, NOT .modelled_revenue. View B's raw shapes use .modelled_revenue directly - View A and View B are NOT parallel. Always grep for an existing working consumer before writing new code that reads a field.
- Every ScrollToSectionLink (or direct scroll_to_section() call) into "How the Numbers Are Calculated" needs pre_toggle_labels: ["Show breakdown"] - that whole area is gated behind a plain button first, not just nested CollapsibleSections.
- The per_source selector explicitly lists every field it returns - a new field on the hook's raw return object will NOT reach the Card unless also added in businessOutcomePerSourceRevenueSelectors.js.
- Per-source direct/overhead cost IS genuinely tracked separately (direct_cost, overhead_share, summed to true_cost) - confirmed 2026-09-12, this is real data any future CFO-metric work can build on honestly.
