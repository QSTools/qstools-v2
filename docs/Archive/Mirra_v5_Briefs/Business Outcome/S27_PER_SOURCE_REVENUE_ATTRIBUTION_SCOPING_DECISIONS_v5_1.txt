# 2. DECISION 1 - MIXED GROUP SPLIT MECHANISM

## What the contract already provides

The split is not something to derive - it already exists at two levels:

- GROUP LEVEL: group_cost_stacks[] (Variable Contract Section 31) carries
  labour and asset as separate fields on the same row -
  assigned_labour_cost, assigned_labour_hours, assigned_asset_burden,
  assigned_asset_hours, assigned_overhead_amount, summed into
  total_group_cost. A mixed group's cost is never a single blended figure
  at this level.

- ASSIGNMENT LEVEL (the one to actually build against): underneath every
  group_cost_stacks row sit labour_assignments[] (Section 20.7) and
  productive_asset_assignments[] / shared_asset_allocations[]
  (Sections 20.8-20.9), each row keyed by staff_type_id or asset_id
  individually, each carrying its own assigned_labour_cost /
  assigned_productive_hours or assigned_asset_burden. Per-source
  attribution data already exists one level below the group rollup.

## Decision

Build the per-source hook against the ASSIGNMENT-LEVEL arrays
(labour_assignments[], productive_asset_assignments[] /
shared_asset_allocations[]), not by reverse-splitting group_cost_stacks.
A mixed group like "2inc Line" (Labour recovery $93,766 + Asset recovery
$33,413, confirmed live) should already resolve into separate assignment
rows per staff type / asset feeding that one group total - read those
rows directly rather than re-deriving a split that already exists
upstream.

## What still must happen before code is written (NOT resolved by this
   note)

This decision is made against the v4.0 VARIABLE CONTRACT documents, which
describe the intended/spec shape. It has NOT been verified against the
live implementation of costAllocationGroupCostBuilder.js in the current

- If the live shape has drifted from the v4.0 contract (plausible, given

# 3. DECISION 2 - UNASSIGNED / RESIDUAL COST PLACEMENT

## What the contract already provides

The "explicit, never-hidden remainder" pattern already exists twice in the
current contract:

- general_overheads_pool (Variable Contract Section 20.6) carries
  remaining_overhead_pool_amount as its own named field - the contract's
  own convention is a visible remainder, not silent absorption.
- unassigned_labour_cost / unassigned_asset_cost warnings are an already-
  established pattern, referenced in S18 as the existing mechanism the
  non-productive labour/asset warnings were built to extend.

## Decision

Adopt S26 Section 5's option (b), as recommended in that brief:

- Residual (undistributed) overhead folds into the materials stream, per
  S23 Section 7 (already locked - overhead not distributed to labour/asset
  pools has no dedicated pool of its own and lands against material).
- Unassigned labour cost and unassigned asset cost each get their own
  explicit line in the per-source reconciliation - never folded into a
  named source, never absorbed into materials, never rounded away.

This is consistent with the existing remaining_overhead_pool_amount
convention rather than inventing a new rule, and keeps the two questions
(where does unallocated overhead go vs where does unassigned direct cost
go) answered separately, since they are different situations - one is
overhead Cost Allocation chose not to distribute, the other is real
labour/asset cost that was never assigned to a group at all.

## What still must happen before code is written

- Confirm unassignedLabourCost / unassignedAssetCost are live, populated
  fields in useBusinessOutcomeWaterfall.js (the handover marks this as
  "likely reusable as-is" but not confirmed) before wiring them into the
  new per-source reconciliation lines.
