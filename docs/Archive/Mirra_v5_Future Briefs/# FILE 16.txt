# FILE 16

# QS Tools — Pre-Database Alignment, Schema Lock & No-Realignment Build Process Brief

## Version: v1.0 — DRAFT FOR LOCK

## STATUS

PRE-DATABASE CONTROL BRIEF

This brief becomes locked only after the variable audit, Business Outcome contract, Modelling contract, question-to-data matrix, and draft schemas have been validated together.

---

## PURPOSE

This brief defines the mandatory process QS Tools must follow before building and locking its persistent application database and historical reporting layer.

Its purpose is to prevent:

* major database redesign after implementation
* repeated module realignment
* duplicated calculation logic
* missing fields discovered too late
* incompatible Business Outcome and Modelling requirements
* weak historical reconstruction
* unstable identities
* broken downstream contracts
* expensive data migrations
* AI and Dashboard requirements being added retrospectively

This is the controlling build-process brief for database readiness.

---

## CORE OBJECTIVE

QS Tools must design the database only after confirming that the entire business system can be represented consistently across:

* current input modules
* calculation modules
* Cost Summary
* Revenue and COG truth
* Business Outcome
* Business Modelling
* Dashboard
* historical reporting
* AI structured context
* baseline, actual, target, and scenarios

The goal is not to predict every future feature.

The goal is to ensure the core architecture is sufficiently complete, extensible, versioned, and traceable so future development can be handled through controlled additions rather than major structural realignment.

---

## CORE NO-REALIGNMENT RULE

The database must not be locked until all of the following have been mapped and validated together:

* core business questions
* current module variables
* missing variables
* stable identities
* module ownership
* Business Outcome outputs
* Modelling inputs and outputs
* baseline, actual, target, and scenario states
* historical reconstruction requirements
* reporting facts and dimensions
* Dashboard data requirements
* AI context requirements
* calculation and contract versions
* source lineage
* reconciliation requirements

---

## SYSTEM PRINCIPLE

The required sequence is:

Business questions
→ required outputs
→ required measures and dimensions
→ variable audit
→ ownership assignment
→ missing-variable alignment
→ output-contract lock
→ database entity design
→ reporting schema design
→ reconstruction proof
→ integration proof
→ schema lock
→ implementation

The sequence must not be reversed.

---

# SECTION 1 — PROTECTED EXISTING SYSTEM

## 1.1 Existing modules must be preserved

The current QS Tools modules and their calculation ownership must be treated as the starting source of truth.

The database build must not become an excuse to rewrite working modules unnecessarily.

Existing calculations must remain in their approved owning locations unless a formal alignment review proves that ownership is incorrect.

---

## 1.2 Active source briefs must be frozen

Before the database audit begins, record the active versions of:

* system briefs
* module source-of-truth briefs
* calculation contracts
* output contracts
* naming conventions
* build-order briefs
* current implemented-state briefs

The audit must be performed against this frozen reference set.

---

## 1.3 Current contract names must be protected

Existing approved internal variable and contract names must not be casually renamed.

Where a rename is required, it must include:

* reason
* old name
* new name
* owning module
* affected consumers
* migration plan
* compatibility period
* contract-version change

Display labels may change without changing internal contract names.

---

# SECTION 2 — PRE-DATABASE DESIGN SEQUENCE

## STAGE 1 — Freeze the active system state

Produce a dated record of:

* active modules
* active source briefs
* current routes
* current calculations
* current selectors
* current storage mechanisms
* current output contracts
* current warnings
* current implemented-state status

### Stage 1 deliverable

Active System Reference Pack.

### Stage 1 gate

No audit begins until the reference pack is confirmed.

---

## STAGE 2 — Lock the Core Business Question Catalogue

Confirm the business-question catalogue covers the decisions QS Tools is expected to support.

Questions must remain grouped by patterns such as:

* revenue
* profitability
* cost
* labour
* productivity
* pricing
* recovery
* supplier
* customer
* asset
* overhead
* baseline
* target
* historical comparison
* risk
* strategic action

### Stage 2 deliverable

Approved Core Business Question Catalogue.

### Stage 2 gate

The catalogue must cover current-state, historical, comparison, scenario, and recommendation questions.

---

## STAGE 3 — Run the Variable Audit

Audit the actual codebase and active briefs.

For every variable, record:

* name
* owning module
* source file
* data type
* unit
* identity
* calculation owner
* persistent status
* versioning requirement
* effective-date requirement
* output-contract status
* downstream consumers
* Business Outcome requirement
* Modelling requirement
* reporting requirement
* Dashboard requirement
* AI requirement
* historical reconstruction requirement
* present, missing, duplicated, or deprecated status

### Stage 3 deliverable

Completed Variable Audit Register.

### Stage 3 gate

Every current business-critical variable must have one clear owner.

---

## STAGE 4 — Confirm stable identities

Before tables are designed, define stable identities for all entities that may change over time.

These may include:

* tenant
* business
* user
* staff member
* labour role
* supplier
* customer
* account
* revenue stream
* cost type
* asset
* asset group
* operating group
* working unit
* profile
* financial period
* baseline
* target
* model
* scenario
* import batch
* calculation version
* contract version

### Identity rule

Names are labels.

IDs are identities.

A renamed staff member, supplier, asset, revenue stream, or operating group must retain the same stable identity where it remains the same underlying entity.

### Stage 4 deliverable

Identity and Relationship Register.

### Stage 4 gate

No versioned entity may rely on a display name as its primary identity.

---

## STAGE 5 — Lock the Business Outcome contract

Business Outcome must be fully defined before database design is locked.

Confirm:

* exact source contracts
* exact headline outputs
* exact contribution outputs
* exact driver outputs
* gross-profit split
* operating-group requirements
* revenue-stream requirements
* data-quality outputs
* warning outputs
* downstream consumers
* historical snapshot requirements

### Stage 5 deliverable

Approved Business Outcome Output Contract.

### Stage 5 gate

Every Business Outcome value must be sourced, owned, and traceable.

---

## STAGE 6 — Lock the Modelling and Scenario contract

Confirm:

* editable modelling levers

* operating constraints
* external assumptions
* scenario identities
* target identities
* baseline references
* scenario outputs
* comparison outputs
* feasibility tests
* transition costs
* interaction effects
* target-promotion rules

### Stage 6 deliverable

Approved Business Modelling and Scenario Contract.

### Stage 6 gate

The scenario engine must be capable of regenerating a complete scenario Business Outcome without altering actual data.

---

## STAGE 7 — Complete the Question-to-Data Coverage Matrix

Map each question category to:

* required measures
* required dimensions
* required grain
* required period
* required source layer
* required calculation owner
* required historical facts
* required operational facts
* required commercial facts
* required scenario variables
* required external data
* current support status
* identified gap
* proposed owner
* implementation phase

### Stage 7 deliverable

Completed Question-to-Data Coverage Matrix.

### Stage 7 gate

---

## STAGE 8 — Classify every identified gap

Every gap must be classified as one of:

* missing persistent input
* missing identity
* missing classification
* missing effective date
* missing version field
* missing source lineage
* missing derived output
* missing Business Outcome output
* missing Modelling variable
* missing reporting fact
* missing reporting dimension
* missing historical grain
* missing commercial behaviour data
* missing external data
* missing AI context output
* unsupported future requirement

### Stage 8 deliverable

Consolidated Gap Register.

### Stage 8 gate

Every gap must have one proposed owner and one proposed destination layer.

---

## STAGE 9 — Align missing module variables

Where the audit identifies true module gaps, add them to their proper owning module before the database schema is locked.

A variable belongs in a module only where that module owns:

* the input
* the calculation
* the warning
* the output contract

A variable must not be added to a module merely because reporting or AI needs to view it.

### Possible destinations

* owning input module
* downstream calculation layer
* Business Outcome
* Modelling
* application database metadata
* reporting dimension
* reporting fact
* structured AI context

### Stage 9 deliverable

Approved Variable Alignment Change Set.

### Stage 9 gate

No unresolved ownership disputes may remain.

---

* module totals
* Cost Summary
* revenue and COG truth
* Business Outcome
* baseline
* actual
* target
* scenario
* Dashboard headline values
* historical snapshot outputs

Run known-answer tests using fixed approved examples.

### Required test types

* module known-answer test
* cross-module reconciliation test
* baseline reconstruction test
* target-model test
* scenario test

* reporting aggregation test
* structured-context parity test

### Stage 10 deliverable

* the variable audit is complete
* stable identities are defined
* Business Outcome is defined
* Modelling is defined
* the question matrix is complete
* gaps are classified
* ownership is assigned
* required module alignment is complete
* known-answer tests pass
* historical reconstruction is proven
* reporting coverage is proven
* Dashboard contracts are proven
* AI context generation is proven
* material variances are resolved
* migration risks are documented

---

The lock pack must contain:

1. approved application entity map
2. approved persistent field register
3. approved identity register
4. approved versioning model
5. approved effective-date model
6. approved baseline/actual/target/scenario model
7. approved fact table map
8. approved dimension map

# SECTION 7 — POST-LOCK CHANGE CONTROL

## ADDITIVE-FIRST RULE

After schema lock, future changes should normally use:

* new optional fields
* new child tables
* new dimensions
* new fact tables
* new contract versions
* new calculation versions
* controlled indexes
* controlled lookup values

The first response to a new feature must not be to redesign the core schema.

---

## MIGRATION RULE

A post-lock change requires a migration brief where it affects:

* stable identity
* tenant ownership
* historical versions
* baseline
* actual
* target
* scenario
* module ownership
* calculation contracts
* output contracts
* fact-table grain
* dimension identity
* source lineage

---

## BREAKING CHANGE RULE

A change is breaking where it:

* renames a contract field
* changes a field’s meaning
* changes a unit
* changes calculation ownership
* changes table ownership
* changes fact grain
* merges identities
* splits identities
* changes baseline interpretation
* changes scenario interpretation
* invalidates historical reconstruction

Breaking changes require:

* impact assessment
* migration script
* compatibility plan
* test plan
* rollback plan
* version increment

---

## COMPATIBILITY RULE

Where practical, a new contract version must temporarily support both:

* old consumer contract
* new consumer contract

The old contract may only be removed after all known consumers are migrated and tested.

---

## NO AD HOC DATABASE CHANGES

Developers must not add fields directly because:

* a page needs a label
* AI needs more context
* one report needs a temporary value
* a calculation is difficult to access
* a new UI component needs local state

Every permanent field must have:

* purpose
* owner
* layer
* source
* type
* history rule
* downstream use
* migration status

---

# SECTION 8 — REALIGNMENT RISK CHECK

Before any major implementation phase, ask:

* Does this change alter a stable identity?
* Does this change alter calculation ownership?
* Does this change affect Business Outcome?
* Does this change affect Modelling?
* Does this change affect historical reconstruction?
* Does this change affect fact grain?
* Does this change affect baseline, actual, target, or scenario separation?
* Does this change create duplicate business truth?
* Does this change require a schema migration?
* Can this requirement be handled additively?

If multiple answers indicate structural impact, the change must return to architecture review before implementation.

---

# SECTION 9 — RESPONSIBILITY MODEL

## Modules own

* user inputs
* module calculations
* module warnings
* module output contracts

## Cost Summary owns

* consolidated business cost structure
* recovery requirements
* cost-burden outputs

## Business Outcome owns

* current commercial outcome
* revenue and COG combination
* contribution outputs
* deterministic drivers

## Modelling owns

* scenario assumptions
* target assumptions
* scenario calculations
* feasibility
* comparisons

## Application Database owns

* persistent state
* identities
* versions
* effective dates
* audit history

## Reporting Layer owns

* historical facts
* analytical dimensions
* trend and comparison data

## Dashboard owns

* presentation
* navigation
* filtering
* drilldown

## AI owns

* explanation
* summarisation
* prioritised advisory recommendations

AI does not own authoritative financial calculations or stored business truth.

---

# SECTION 10 — NO-GO CONDITIONS

Database implementation must not begin where any of the following remain unresolved:

* unknown calculation ownership
* duplicated variable meaning
* unstable identities
* missing Business Outcome requirements
* missing Modelling requirements
* undefined baseline rules
* undefined scenario rules
* undefined effective-date rules
* undefined historical grain
* unresolved material reconciliation variance
* unproven historical reconstruction
* unproven Dashboard contract
* unproven AI context
* unclassified critical gaps
* missing migration strategy

The pre-database alignment process is complete only when:

* the active system state is frozen
* the question catalogue is approved
* the variable audit is complete
* stable identities are locked
* Business Outcome is locked
* Modelling is locked
* the question matrix is complete
* all gaps are classified
* ownership is assigned
* required module alignment is complete
* reconciliations pass
* known-answer tests pass
* the application database is mapped
* the reporting schema is mapped
* historical reconstruction is proven
* baseline, actual, target, and scenarios are proven
* Dashboard integration is proven
* AI context generation is proven
* schema version 1 is approved
* the migration and change-control process is approved

---

# FINAL CONTROL STATEMENT

QS Tools must not build its permanent database by transferring the current browser state directly into tables.

The database must be designed only after the business questions, variables, identities, outputs, scenarios, historical requirements, reporting requirements, Dashboard requirements, and AI requirements have been aligned as one system.

This process is the primary safeguard against a major future realignment.

After schema lock, future development must favour additive extension, controlled contract versions, and explicit migrations rather than repeated redesign of the core business architecture.
