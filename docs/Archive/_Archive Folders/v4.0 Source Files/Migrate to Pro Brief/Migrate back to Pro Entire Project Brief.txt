# 1. Master Handover Brief

## Product Vision

QS Tools is a web-based business analysis, recovery, pricing, and quoting tool for contractors and small businesses.

Its core purpose is to **mirror the real business back to the user** by connecting:

* P&L data
* cost structure
* labour cost and productive capacity
* asset cost
* general overheads
* revenue and COGS
* recovery requirement
* cost allocation
* quote checking
* accepted quote feedback

The system is intended to help a business understand whether its pricing, labour charge-out rates, material margins, and recovery strategy actually cover the real cost of operating.

## Current Product Direction

QS Tools is moving toward a **digital CFO / business decision engine**.

It should help answer:

* What does the business really cost to run?
* How much revenue is required?
* What labour rate must be charged?
* What material or product margin is actually being achieved?
* Are overheads being recovered?
* Is a quote profitable before acceptance?
* Did accepted quotes perform against the model?

## Current Working Name

The current working name is **QS Tools / QSTools**.

Future brand names have been discussed separately, but the codebase, source files, and briefs still use QS Tools.

## Current Locked System Principle

The latest active architecture separates the system into:

```text
Cost Summary = WHAT it costs
Recovery Summary = HOW it is recovered
Cost Allocation = CAN it be delivered
Recovery Outcome = SHOULD you run it
```

The active v1.17 system brief locks the current architecture as:

```text
INPUT MODULES
↓
COST SUMMARY
↓
RECOVERY SUMMARY
↓
COST ALLOCATION
↓
RECOVERY OUTCOME
↓
BUDGET
```

# 2. Architecture Brief

## Stack

QS Tools is built as a Next.js App Router application using React client components, hooks, selectors, calculation libraries, localStorage, and a token-based CSS/UI system.

## Standard Module Structure

New modules must follow this file structure:

```text
app/<module>/page.jsx
hooks/use<Module>.js
lib/calculations/<module>Calculations.js
lib/selectors/<module>Selectors.js
lib/storage/<module>Storage.js
lib/storage/<module>ProfileStorage.js
components/<module>/
  <Module>StatusStrip.jsx
  <Module>MainCard.jsx
  <Module>HelpPanel.jsx
```

This structure is locked in the New Module Build Template. 

## Architecture Separation Rule

The locked separation is:

```text
page = layout + orchestration only
hook = integration / orchestration
selectors = shaping
calculations = business logic
components = UI only
```

No business logic should live in `page.jsx` or UI components. 

## Naming Rules

The naming convention brief locks:

* folder names: `kebab-case`
* React/module names: `PascalCase`
* variables: `snake_case`
* IDs: `_id` format
* hooks: `use<Module>.js`
* calculations: `<module>Calculations.js`
* selectors: `<module>Selectors.js`
* components must use the module prefix

Examples of locked output contract names include:

```text
gross_wages_annual
total_people_cost_annual
employee_overheads_total_annual
productive_labour_cost_rate
minimum_charge_out_rate
total_cost_burden
required_recovery_rate
```



## Downstream Contract Rule

The most important architectural rule is:

```text
Upstream modules own inputs, calculations, and output contracts.
Downstream modules consume outputs only.
No downstream module may rebuild upstream maths.
No downstream module may rename contract variables.
```

This is explicitly locked in the v1.17 active system brief and guardrail brief. 

## UI System

The UI system is token-based and must not drift.

Locked UI rules:

* no inline styles
* no hardcoded colours
* no `text-white`
* no `bg-neutral-*` hacks
* use CSS tokens
* use standard UI classes
* mobile-first layout
* macro → breakdown → drilldown

The UI system brief locks the token-driven structure and standard UI classes such as `ui-section`, `ui-panel`, `ui-input`, `ui-button-primary`, `ui-pill`, `ui-kicker`, and `ui-stack`.

* Assets benchmark
* General overheads

```text
non_productive_paid_hours =
annual_leave_weeks × hours_per_week
+ public_holiday_days × daily_hours
+ sick_days × daily_hours
+ bereavement_days × daily_hours
```

```text
productive_hours =
(paid_hours_per_year - non_productive_paid_hours)
× productivity_percent / 100
```

Total employer labour cost includes:

* `gross_wages_annual`
* `entitlements_annual`
* `employer_kiwisaver_gross`
* `esct_amount`
* `total_employer_contribution_cost`
* `productive_hours`

Labour v1.9 is implemented and exposes these downstream outputs. 

## Minimum Charge-Out Logic

```text
productive_labour_cost_rate =
total_labour_cost_annual / productive_hours

minimum_charge_out_rate =
productive_labour_cost_rate / (1 - margin_target_percent)
```

## Asset Finance Logic

Assets use real cash cost recovery. Depreciation is excluded.

Asset outputs:

* `finance_cost_annual`
* `running_cost_annual`
* `total_asset_cost_annual`

## General Overheads Logic

General Overheads produce:

```text
total_general_overheads
```

Cost Summary maps:

```text
total_business_overheads = total_general_overheads
```

## Cost Burden Logic

Cost Summary v1.7 locks:

```text
total_business_cost_annual =
total_asset_cost_annual + total_business_overheads

total_cost_burden =
total_people_cost_annual
+ total_asset_cost_annual
+ total_business_overheads

required_revenue =
total_cost_burden

required_recovery_rate =
required_revenue / total_productive_output
```



## Recovery Logic

Recovery Summary distributes cost burden:

```text
labour_recovery_cost =
total_cost_burden × labour_share_percent / 100

asset_recovery_cost =
total_cost_burden × asset_share_percent / 100

overhead_absorbed_cost =
total_cost_burden × overhead_share_percent / 100

required_labour_recovery_rate =
labour_recovery_cost / total_productive_output
```



## Cost Allocation Logic

Cost Allocation validates structure:

* links staff to assets
* defines operational groups
* detects duplicate links
* detects orphan staff/assets
* validates group completeness
* calculates coverage percentages

It does not calculate cost or recovery.

## Recovery Outcome Logic

Recovery Outcome decision flow:

* invalid share model → `not_viable`
* no productive/labour base → `not_viable`
* asset/hybrid strategy with invalid structure → `not_viable`
* asset strategy without assets → `not_viable` or `marginal`
* weak coverage → `marginal`
* no blocking issues → `viable`



## Quote Checker Logic

Future Quote Checker should test quotes against:

* required labour recovery
* minimum charge-out
* material/product margin
* direct costs
* target margin
* business recovery burden

It should not confuse material markup with overhead recovery.

## Feedback Loop Logic

Accepted quotes only should feed actual-vs-model performance:

* labour hours actual vs allowed
* materials actual margin vs expected
* total quote margin vs model
* monthly roll-up
* pricing improvement signal
