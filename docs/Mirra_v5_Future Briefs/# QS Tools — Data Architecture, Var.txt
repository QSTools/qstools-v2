# QS Tools — Data Architecture, Variable Audit & Reporting Readiness Brief (v1.0 — LOCKED)

## STATUS

NEW CONTROL BRIEF

---

## PURPOSE

This brief defines the data-design work required before building the QS Tools persistent database and reporting layer.

It exists to ensure the system can:

* persist all user-entered module data safely
* reconstruct the business model at any historical point in time
* support Business Outcome and Modelling correctly
* support dashboard, historical reporting, and AI questions
* identify missing variables before database build
* prevent underbuilding or overbuilding the data model

This brief is a system-design brief, not a UI brief.

---

## CORE PRINCIPLE

QS Tools must support **three connected layers**:

1. **Application data layer**
   stores user inputs, versions, assumptions, and module states

2. **Calculated model layer**
   rebuilds the business model from stored inputs at any point in time

3. **Reporting / analytics layer**
   stores historical outputs and financial facts for dashboard, comparisons, and trends

The system must never confuse these layers.

---

## DEFINITIONS

### Application Database

The operational database that stores all persistent user-entered or system-owned state required to rebuild the business.

### Structured Output

The runtime business model generated from the calculation engine for a current or requested point in time. This is the JSON-style structured context used by the UI and AI layer.

### Historical Reporting Layer

The star-schema style reporting layer used to analyse performance over time.

### Baseline

The original locked business model state at the point the business was first structured.

### Actual

The real performance and real input changes that occur after baseline.

### Target / Model

The desired future state defined in the Modelling layer.

---

## SYSTEM RULES

### Rule 1 — Do not build the database until variable coverage is checked

Before the database is designed, QS Tools must confirm:

* which variables already exist
* which variables are still missing
* which variables are required for Business Outcome
* which variables are required for Modelling
* which variables are required for reporting
* which variables are required for AI explanation

### Rule 2 — Inputs and outputs must be treated differently

Inputs must be stored in the application database.
Outputs must be generated by the calculation engine.
Only selected outputs should be stored in the reporting layer.

### Rule 3 — Historical JSON files are not stored

Historical structured outputs must be reconstructed from versioned inputs and historical facts when required.

### Rule 4 — Dashboard and AI must not rely on reporting tables for structural explanation

Dashboard current state and AI structural reasoning must use the calculated structured model.
The reporting layer is used for trend, comparison, and history.

### Rule 5 — Star schema is for history, not for rebuilding the business

The reporting layer must never become the source of truth for module reconstruction.

---

## OBJECTIVES OF THIS BRIEF

This brief must enable QS Tools to answer three classes of question:

### A. Structural questions

Examples:

* What makes this number up?
* Why am I losing money?
* What is the biggest driver of profit pressure?
* Where is pricing headroom?

These depend on the calculated model.

### B. Historical questions

Examples:

* How has revenue changed by month, quarter, and year?
* What changed between Q1 2025 and Q1 2026?
* Which supplier is becoming a larger percentage of COG over time?

These depend on the reporting layer.

### C. Comparison / AI questions

Examples:

* Why was this quarter stronger than the same quarter last year?
* What is the biggest reason actual differs from target?
* If I could change one thing to improve profit, what would it be?

These depend on both the reporting layer and rebuilt model snapshots.

## REQUIRED WORKSTREAMS

The data-design phase must be completed in the following order:

### 1. Variable Audit

Review current module inputs and outputs and confirm:

* what already exists
* what is still missing
* what is duplicated
* what is poorly named
* what cannot yet be traced cleanly

### 2. Business Outcome Variable Check

Confirm all variables required for Business Outcome exist or are formally identified as missing.

This includes variables required to show:

* current business profitability
* gross profit split
* cost-to-revenue relationships
* major business drivers
* high-level business health

### 3. Modelling Variable Check

Confirm all variables required for Modelling exist or are formally identified as missing.

This includes variables required to show:

* baseline
* target
* actual
* gap to target
* primary improvement levers
* realism constraints

### 4. Reporting Question Matrix

Group likely user questions into categories and identify:

* measures required
* dimensions required
* whether each question is answered from:

  * application data
  * rebuilt model
  * reporting layer
  * combined AI context

### 5. Application Database Design

Design the operational database to store all required module inputs and version history.

### 6. Reporting Layer Design

Design the historical reporting layer to store selected financial and calculated outputs over time.

## VARIABLE AUDIT REQUIREMENTS

The variable audit must review every current QS Tools module and classify each variable into one of the following:

### A. Persistent Input

A user-entered or system-owned value that must be stored in the application database.

Examples:

* labour_rate
* hours_per_week
* purchase_price
* productivity_percent
* overhead values
* modelling target values

### B. Derived Output

A value calculated by the engine that should not be manually stored as input.

Examples:

* productive_hours
* required_recovery_rate
* total_cost_burden
* gross_profit
* margin_gap

### C. Historical Reporting Output

A selected output that should be written to the reporting layer over time.

Examples:

* revenue
* COG
* gross profit
* net profit
* recovery rate
* total cost burden
* productivity
* supplier spend percentage

### D. AI Explanation Output

A derived value that improves reasoning quality and should be available explicitly for AI use.

Examples:

* recovery_gap
* pricing_headroom
* margin_buffer
* primary_driver_key
* primary_constraint_key

### E. Missing Variable

A required value that does not yet exist cleanly in the system.

---

## VARIABLE AUDIT DELIVERABLE

The variable audit must produce a register with at least these columns:

* module
* variable_name
* variable_type
* current_status
* required_for_business_outcome
* required_for_modelling
* required_for_reporting
* required_for_ai
* missing_or_present
* notes

---

## BUSINESS OUTCOME READINESS CHECK

Before Business Outcome is built, QS Tools must confirm it has enough variables to answer:

* what is the business making?
* what is the business costing?
* where is gross profit coming from?
* what is the split of gross profit across the business?
* what are the primary performance drivers?
* what is the current commercial state of the business?

If any required variable is missing, that missing variable must be added to the audit register before Business Outcome build proceeds.

---

## MODELLING READINESS CHECK

Before Modelling is built, QS Tools must confirm it has enough variables to answer:

* where are we today?
* where do we want to be?
* what is the difference?
* which levers move the gap most?
* which targets are realistic?
* which targets are not realistic?
* what single change would improve performance most?

If any required modelling variable is missing, it must be identified before the database design is locked.

## APPLICATION DATABASE DESIGN RULES

The application database must store all values required to reconstruct the business at any point in time.

### It must store:

* business / tenant identity
* module inputs
* module profile versions
* effective dates
* baseline state
* modelling targets
* changed assumptions over time
* user-owned classifications such as supplier, revenue stream, labour type, asset grouping, operating group where relevant

### It must support:

* multi-user / multi-tenant separation
* versioned module inputs
* historical reconstruction
* future integration with imports such as Xero

### It must not:

* depend on browser cache
* use reporting tables as source of truth
* rely on current UI state as long-term storage

---

## REPORTING LAYER DESIGN RULES

The reporting layer must support historical and analytical questions over time.

### It must store:

* imported financial facts
* selected calculated outputs
* time-based business snapshots
* actual vs baseline vs target references where appropriate

### It should answer:

* month / quarter / year trends
* supplier concentration
* revenue and COG changes over time
* margin trends
* recovery trends
* productivity trends
* actual vs target comparison trends

### It must not:

* become the primary application database
* store every module input
* store full historical JSON snapshots
* drive core calculations

---

## REQUIRED QUESTION CATEGORIES FOR DESIGN

The database and reporting design must be capable of supporting these broad question groups:

* revenue and growth
* profitability and margin
* cost structure
* labour and productivity
* pricing and recovery
* supplier concentration and spend
* asset and overhead efficiency
* baseline vs actual vs target
* historical comparison
* strategic decision support
* AI explanation and diagnosis

The design must be based on these categories, not on hardcoded prompt wording.

---

## STRUCTURAL VS HISTORICAL QUESTION RULE

QS Tools must always distinguish between:

### Structural questions

Examples:

* What makes this up?
* Why is profit low?
* Where is pricing headroom?

These come from the rebuilt model.

### Historical questions

Examples:

* How did revenue change by quarter?
* How has supplier share changed over time?
* Was Q1 stronger than Q2?

These come from the reporting layer.

### Combined questions

Examples:

* Why was Q1 2025 better than Q1 2026?
* What changed that caused margin to drop?

These require:

* historical facts
* rebuilt model snapshots
* AI comparison context

---

## DATABASE DESIGN DECISION RULE

Before the database schema is locked, every proposed field must be placed into one of these layers:

### Layer 1 — Application Database

Needed to rebuild the business

### Layer 2 — Rebuilt Model / Structured Output

Needed to explain the business

### Layer 3 — Reporting Layer

Needed to analyse the business over time

If a field does not clearly belong to one of these layers, it must not be added until clarified.

## DEFINITION OF DONE

This brief is complete only when:

* current variables have been audited
* missing variables have been identified
* Business Outcome readiness is confirmed
* Modelling readiness is confirmed
* data layers are separated clearly
* application database needs are defined
* reporting layer needs are defined
* question categories are mapped to required data
* future AI and dashboard requirements are covered

---

## FINAL DEFINITION

QS Tools must not build its persistent database or reporting layer blindly.
It must first audit variables, confirm Business Outcome and Modelling requirements, and design data storage around the questions the system must answer. The application database must preserve all data required to rebuild the business, while the reporting layer must preserve the selected financial and calculated outputs required to analyse the business over time.
