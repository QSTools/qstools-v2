# FILE 7

# QS Tools — Dashboard Data Contract Brief

## Version: v1.0 — DRAFT FOR LOCK

## PURPOSE

This brief defines the data contract for the QS Tools Dashboard, which will operate as the primary landing page for a business.

The Dashboard must combine:

* current business state
* locked baseline
* approved target
* performance gap
* Business Outcome
* structural drilldown
* historical trends
* warnings
* embedded AI access

The Dashboard does not own calculations.

---

## CORE DASHBOARD QUESTIONS

The Dashboard must answer:

* Where is the business now?
* What was the approved baseline?
* What is the current target?
* How are we tracking against baseline?
* How are we tracking against target?
* What is driving the result?
* What changed over time?
* What requires attention?
* What question should the user ask next?

---

## DATA SOURCES

### Current Structural Data

Source:

* current structured calculated model

Used for:

* current totals
* cost composition
* profitability
* recovery
* current warnings
* structural drilldown

### Baseline Data

Source:

* approved locked baseline model

Used for:

* original comparison
* baseline variance
* baseline assumption review

### Target Data

Source:

* active approved target model

Used for:

* progress tracking
* target gap
* future requirements

### Historical Data

Source:

* reporting layer

Used for:

* trends
* month comparisons
* quarter comparisons
* year comparisons
* supplier/customer/revenue-stream analysis

---

## DASHBOARD HEADLINE CONTRACT

The headline layer should support:

* actual revenue
* baseline revenue
* target revenue
* actual COG
* baseline COG
* target COG
* actual gross profit
* baseline gross profit
* target gross profit
* actual gross margin
* baseline gross margin
* target gross margin
* total cost burden
* required recovery
* achieved recovery where available
* profit gap
* recovery gap
* current data period
* data completeness status

---

## BUSINESS OUTCOME CONTRACT

The Dashboard must be capable of displaying the outputs created by Business Outcome, including:

* gross-profit split
* contribution by revenue stream
* contribution by operating group where available
* cost absorption
* people-cost share
* asset-cost share
* overhead share
* strongest contribution area
* weakest contribution area
* current primary driver
* material constraints

---

## MODELLING CONTRACT

The Dashboard must consume approved Modelling outputs such as:

* target revenue
* target COG
* target gross profit
* target margin
* target productive capacity
* target recovery
* target rate or rate mix
* target cost reductions
* target productivity improvement
* realistic constraint state
* active model version

---

## VARIANCE CONTRACT

The Dashboard must receive pre-calculated comparison values.

Examples:

* actual_minus_baseline
* actual_minus_target
* percentage_variance_to_baseline
* percentage_variance_to_target
* target_progress_percent
* revenue_gap
* COG_gap
* gross_profit_gap
* margin_gap
* productivity_gap
* recovery_gap

The Dashboard must not calculate business variances inside UI components.

---

## DRILLDOWN RULES

### Structural Drilldown

Answers:

* What makes this up?
* Why is this value high or low?

Source:

* structured model and calculation trace

### Historical Drilldown

Answers:

* How did this change?
* When did this change?
* Which period or category caused the movement?

Source:

* historical reporting layer

### Source Drilldown

Answers:

* Which input or source record created this result?

Source:

* application database lineage and effective-dated records

---

## DASHBOARD SECTIONS

Recommended top-level sections:

1. business status
2. baseline versus actual versus target
3. revenue and COG
4. gross profit and margin
5. cost and recovery
6. Business Outcome contribution split
7. key variances
8. historical trends
9. warnings and data completeness
10. Ask Your Business AI

---

## TIME CONTROLS

The Dashboard should support:

* current month
* current quarter
* financial year to date
* prior comparable period
* custom range
* baseline period
* target period

Time controls must clearly identify whether a value is:

* live
* closed period
* year to date
* baseline
* target
* forecast
* scenario

---

## REFRESH AND CLOSE RULE

Live values may update as inputs change.

Historical reporting values should distinguish between:

* open period
* provisional close
* approved close
* restated period

The Dashboard must not present provisional and approved figures as equivalent without a visible status.

---

## AI ENTRY POINT

The Dashboard should provide embedded AI access to the currently selected business, period, filters, and scenario.

Suggested questions may be generated from:

* material warnings
* major variances
* top drivers
* unusual trends
* target gaps

The AI layer must use the same underlying numbers shown on the Dashboard.

---

## NOT ALLOWED

* business calculations inside Dashboard components
* separate Dashboard-only versions of core metrics
* AI answers based on values different from those displayed
* mixing baseline, actual, and target without labels
* historical charts built from current-only data
* hiding incomplete or provisional data status
* using reporting tables for current structural calculations
* using current structured data as a substitute for historical facts

---

## DEFINITION OF DONE

The Dashboard Data Contract is ready when:

* baseline, actual, and target are clearly separated
* Business Outcome outputs are available
* Modelling outputs are available
* current structural drilldown works
* historical drilldown works
* source traceability works
* warnings are visible
* AI uses the selected Dashboard context
* headline totals reconcile with the underlying engine

---

## FINAL DEFINITION

The Dashboard is the primary decision surface of QS Tools. It presents current truth, locked baseline, approved target, historical performance, and Business Outcome from shared system contracts without owning or duplicating calculation logic.

============================================================

# QS Tools — Variable Audit Register & Readiness Template

## Version: v1.0 — WORKING TEMPLATE

## PURPOSE

This register is the working control document used to determine whether the current QS Tools variables are sufficient for:

* Business Outcome
* Business Modelling
* application database design
* historical reporting
* Dashboard
* AI explanation
* historical reconstruction

The register must be completed against the actual codebase and current active source briefs.

---

## AUDIT SCOPE

Audit:

* module inputs
* module outputs
* identities
* storage fields
* profile fields
* selectors
* calculation results
* warnings
* Dashboard requirements
* Business Outcome requirements
* Modelling requirements
* reporting requirements
* AI requirements

These values should only be added where they represent stable, useful business outputs. AI must not be used to invent them.

---

## AUDIT PROCESS

### Step 1 — Extract

Extract current variables from:

* calculations
* selectors
* hooks
* storage
* output contracts
* active briefs

### Step 2 — Normalise

Check:

* naming
* duplicates
* units
* ownership
* identity
* output consistency

### Step 3 — Map

Map every variable to:

* Business Outcome
* Modelling
* Dashboard
* reporting
* AI
* historical reconstruction

### Step 4 — Identify Gaps

Classify each gap as:

* missing input
* missing dimension
* missing derived output
* missing history field
* missing version field
* missing lineage field

### Step 5 — Assign Ownership

Every missing variable must have one clear owning module or downstream layer.

### Step 6 — Approve

Do not add variables until ownership, naming, formula, storage, and downstream use are approved.

---

## READINESS GATES

### Business Outcome Ready

All required Business Outcome values are present, owned, and reconciled.

### Modelling Ready

All required baseline, target, constraint, and variance values are present and owned.

### Database Ready

All persistent entities, identities, versions, and effective dates are defined.

### Reporting Ready

All required facts, dimensions, grains, and source mappings are defined.

### AI Ready

Current and historical context can be assembled with complete lineage and data-quality status.

---

## NOT ALLOWED

* adding variables without ownership
* creating duplicate names for the same concept
* adding reporting-only fields into unrelated calculation modules
* using display labels as contracts
* changing locked names without migration
* marking a requirement complete because it appears only in UI text
* assuming AI can compensate for missing source data
* locking the database before Business Outcome and Modelling gaps are understood

---

## DEFINITION OF DONE

The variable audit is complete when:

* every current variable is registered
* duplicates and conflicts are resolved
* Business Outcome gaps are known
* Modelling gaps are known
* database fields are known
* reporting measures and dimensions are known
* AI explanation outputs are known
* ownership is assigned
* approved additions are ready for implementation

---

## FINAL DEFINITION

The Variable Audit Register is the control mechanism that prevents QS Tools from building Business Outcome, Modelling, the database, reporting, the Dashboard, or AI on incomplete or duplicated data contracts.
