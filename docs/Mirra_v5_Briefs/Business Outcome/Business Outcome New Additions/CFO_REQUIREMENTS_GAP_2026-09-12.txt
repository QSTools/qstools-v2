# CFO Requirements Gap - Business Outcome (2026-09-12)

## Why this exists
Business Outcome is intended for eventual CFO adoption. This document is a scoping exercise, not a build brief: what standard CFO assessment tools/terminology already exist correctly on this page, what's real but unlabeled, and what's genuinely missing - with honest notes on whether the gap is a labeling fix, a build task, or blocked on data that doesn't exist yet. Written 2026-09-12 alongside the Health Gauge terminology work that triggered this review.

## IMPORTANT - live data context
Mirra is currently run session-by-session against manually-entered or single-snapshot-imported data (Labour, Assets, current Xero COGS pull). The Revenue/COGS module already imports 12 months of dated, per-supplier Xero data on each import - this is the one area with genuine historical depth today. Labour and Asset hours have NO dated/historical tracking - only current-state snapshots.

The user has confirmed two things are coming, not hypothetical:
1. [SHIPPED 2026-09-12] Balance sheet import from Xero - DONE, see Part 3 below for full detail. Currently Excel-file import (Xero trial/API access still pending), not yet a live API pull.
2. Live, ongoing data flow (not just periodic manual re-entry) - the system will eventually be fed continuously rather than snapshotted per session.

**Design implication: anything built against "the current snapshot" from here on should be built assuming it will later run against a live, updating feed, not a one-off import.** Where reasonably possible, calculations and any new UI should not hard-assume "this number was computed once and is now static" - prefer designs that would naturally re-compute correctly if the underlying data started updating more frequently, rather than baking in an implicit "annual snapshot" assumption that would need unpicking later. This is a design lens to apply going forward, not a mandate to rebuild anything that already works.

## Part 3 - Genuinely missing, feasibility assessed

| Concept | Standard CFO use | Feasibility | Notes |
|---|---|---|---|
| EBITDA by unit/segment | Standard tool for cross-subsidy/segment analysis - exactly what the Health Gauge is informally approximating | Needs scoping | Confirmed zero hits in codebase. BusinessOutcomeNetProfitBuildUp.jsx is the closest existing analog (per-source net profit) but isn't framed in EBITDA terms. Whether Mirra tracks depreciation/amortisation/interest at a per-source level (required for a true EBITDA-by-unit figure) has NOT been confirmed - needs a data-availability check before this is promised as buildable, not just relabeled. |
| Formal segment reporting | Standard external/internal reporting format - revenue, cost, profit by business segment, typically with defined criteria for what counts as a reportable segment | Needs scoping | Mirra's "operating group" concept (labour/asset groups) is the closest analog and the data likely supports it, but no work has been done to confirm whether groups map cleanly onto what a CFO would call a "segment," or what criteria would define one. |
| Working capital ratios (current ratio, quick ratio, etc.) | Standard liquidity assessment | [SHIPPED 2026-09-12] DONE - no longer blocked. | Full Xero Excel Balance Sheet importer built and live-tested against a real export (lib/imports/xeroBalanceSheetImporter.js), with storage (lib/storage/balanceSheetStorage.js), calculations (lib/calculations/balanceSheetCalculations.js - working_capital, current_ratio, quick_ratio, debt_to_equity, all verified against real data and edge cases), hook (hooks/useBalanceSheet.js), and a full import/display page at /balance-sheet, linked from the sidebar under Business Inputs. Real result against the actual test balance sheet: working capital -$54,035, current ratio 0.80, quick ratio 0.75, debt-to-equity 5.35 - a genuine liquidity flag worth CFO attention. One real bug found and fixed during build: a save-before-load race condition was silently wiping imported data on every page navigation - fixed with a has_loaded guard in the hook. NOTE: this is still Excel-file import, not a live Xero API pull - API access needs a Xero trial/OAuth app, not yet set up. The importer's output shape was deliberately designed to match what a future live API pull would return, so swapping to live data later should mean replacing this file's internals, not reshaping every downstream consumer. |
| Period-over-period / trend analysis | Standard for any CFO review - is the business improving or declining | PARTIALLY feasible today, fully feasible pending live data | Revenue/COGS module already has 12 months of dated, per-supplier Xero data on every import - a revenue/COGS-only trend view could be built today. Labour and Asset hours have no dated/historical tracking at all currently - a full trended profitability view (all three cost legs) is blocked until that exists. This is the single clearest case where "build it in lieu of live data coming" applies: any trend UI built now should be designed to extend naturally once Labour/Assets gain historical tracking, not rebuilt from scratch. |
| Liquidity ratios generally (current, quick, cash ratio) | Standard CFO toolkit | [SHIPPED 2026-09-12] DONE for current ratio and quick ratio (see working capital row above) - cash ratio specifically not yet built (no dedicated "cash and cash equivalents" line was cleanly identifiable in the real test export - bank account balances appeared oddly under Current Liabilities, not Current Assets, in the actual uploaded file - worth a closer look at real chart-of-accounts conventions before building a cash ratio that could be misleading). | Cash ratio is the one liquidity metric NOT yet built - flagged as a real follow-on, not forgotten. |

## Part 4 - Recommended order, if/when this becomes a build

Not a commitment, just a logical sequence given the dependencies above:

1. [DONE 2026-09-12] Balance sheet import - shipped, see Part 3.
2. Revenue/COGS trend view (fully buildable today, no blockers - lowest-risk place to start actual trend UI, and establishes the pattern the fuller trend view will later extend).
3. Labour/Asset historical tracking (a genuine data-model change - dated snapshots instead of current-state-only - needed before the fuller trended profitability view can exist. Likely comparable in size to the Asset Utilisation/Downtime prerequisite from the 2026-09-10/11 session - i.e. "a huge change in the system," not a quick add).
4. Full trended profitability view (revenue + labour + asset + materials, all periods) - depends on #3.
5. EBITDA-by-unit and formal segment reporting - depends on confirming per-source depreciation/amortisation/interest tracking exists or can be added; genuinely needs its own scoping session before any commitment on size.

## What this document is NOT
Not a commitment to build any of Part 3 or Part 4. Not a statement that the current page is CFO-inadequate - Part 1 shows real, correctly-built standard tools already exist. This is a scoping record so that when CFO-readiness work does happen, it starts from an accurate map instead of guessing what's missing.
