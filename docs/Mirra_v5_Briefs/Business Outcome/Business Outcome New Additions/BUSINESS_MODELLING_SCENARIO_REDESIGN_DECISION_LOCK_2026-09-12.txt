# Business Modelling Scenario Redesign - Decision Lock (2026-09-12)

## Why this exists
This session's investigation into "Outcome -> Modelling handoff fields" (session brief Section 2A) surfaced two coexisting, unreconciled systems on the Business Modelling page - the newer live-lever tool (fed from real Business Outcome data) and the older baseline/upside/downside scenario tool (fed from a separate, older Business Summary source, currently collapsed and labeled "being replaced"). This document locks down the actual redesign decision made 2026-09-12, so it can be built correctly whenever that session happens, without re-litigating the decision from scratch.

## The decision

**Keep the three-scenario concept (Baseline / Upside / Downside). Rebuild it to run on the live-lever engine instead of the old Business Summary-fed system. Redefine what each of the three actually means.**

### Baseline
- NOT editable, NOT a guess. It is "where the business actually is right now" - built from Business Outcome's real, live per-source data (the same engine System 2 / the live-lever tool already uses: useBusinessOutcomePerSourceRevenue -> selectBusinessOutcomePerSourceRevenue -> businessModellingLeverSelectors.js).
- Locked at a point in time on purpose, so it stops moving under the user while they compare against it - re-locked periodically (user suggested quarterly review as the cadence) rather than continuously drifting with every live change elsewhere in the system.
- Explicitly replaces the OLD baseline concept, which was built from useBusinessSummary and editable/refreshable at will - the new Baseline is fixed and dated, not a live-refreshing snapshot.

### Upside
- A genuine target scenario - "where we want to get to." Editable, using the live-lever engine's real levers (rate changes, materials markup, utilisation, etc. - the five lever types already confirmed in session brief Section 3.3/S30 Sections 3-4).
- SAVED/persisted (not ephemeral like the current live-lever tool) - this is the explicit reason for keeping scenario persistence at all: "if you go back and alter it the goal posts are always moving" (user, 2026-09-12) - an Upside scenario needs to still be there next time the user opens the page.

### Downside
- COMPLETELY REDEFINED from the old system. No longer a separately-edited pessimistic scenario.
- It is now simply BREAKEVEN, positioned relative to wherever Baseline currently sits:
  - If Baseline shows a net profit -> Downside/breakeven sits BELOW Baseline (how far profit could fall before hitting breakeven).
  - If Baseline shows a net loss -> Downside/breakeven sits ABOVE Baseline (how far the business would need to climb to stop losing money).
- This makes Downside a CALCULATED REFERENCE LINE, not a user-edited scenario - it has no separate lever inputs of its own, it is derived purely from Baseline's position relative to the business's real breakeven revenue (the same breakeven_revenue figure already used throughout Business Outcome - per_source.reconciliation.total_true_cost, confirmed correct in this session's Projected Net Profit verification, session brief item 2).

## What this replaces / retires

The OLD three-scenario system (useBusinessSummary-fed, businessModellingCalculations.js's buildBaselineSnapshot/buildScenarioState, businessModellingStorage.js's save/load, businessModellingSelectors.js's card-building functions) is superseded by this redesign. Once built, the old system's dependencies can be fully removed - not just visually collapsed as "Previous scenario tools" (its current state as of 2026-09-12).

**Do NOT remove the old system's code before the new one is built and verified working against live data** - the collapsed "Previous scenario tools" section stays as a safety net until the replacement is confirmed correct, same caution this session applied to businessModellingIndependentCalculations.js (verify before touching).

## What survives from the old system, conceptually
- The idea of three named, comparable positions (not just "here's the current number" like the live-lever tool alone gives you).
- Persistence - saved scenarios that don't reset on refresh.
- A delta/comparison view between scenarios (the old system's BusinessModellingDeltaCard concept, though its calculation source needs rebuilding against the new engine).

## What does NOT survive
- Business Summary as the data source for any of this - all three scenario positions should be built from the same live Business Outcome per-source data the rest of this page (and Business Outcome itself) already trusts.
- Downside as a manually-edited/guessed scenario - it becomes a calculated line, not an input.
- Continuous baseline refresh - Baseline becomes a periodic, locked snapshot (quarterly suggested), not a live-updating figure.

## Open questions - NOT yet decided, for next scoping pass when this is actually built
1. Exact locking/re-lock mechanism for Baseline - is "quarterly" a hard rule, a suggested default, or user-triggered on demand? Not decided, just proposed as a starting cadence.
2. Where Baseline's locked snapshot is stored, and whether historical Baselines (past quarters) should be kept and comparable to each other - ties into the CFO Requirements Gap document's Period-over-period trend item (CFO_REQUIREMENTS_GAP_2026-09-12.txt, Part 3) - these two pieces of future work likely share the same underlying "store dated snapshots" mechanism and should probably be scoped together, not separately, when the time comes.
3. Exact UI layout - does Upside remain a single editable scenario, or could there be multiple saved Upside variants? Not raised this session, flagged only so it isn't assumed either way.
4. Migration path for any data currently sitting in the old system's storage (businessModellingStorage.js) - whether it's safe to discard or needs any carry-forward. Not checked this session.

## Status
[SHIPPED 2026-09-14] Built and live-verified against real data. Full stack: lib/storage/businessModellingScenarioStorage.js (Baseline history, never deleted, exactly one is_current, single Upside, Downside never stored), lib/calculations/businessModellingScenarioCalculations.js (real Baseline snapshot from live per_source with EMPTY levers, Downside-as-breakeven, Upside headline using its own saved levers not whatever's currently live-editable), hooks/useBusinessModellingScenario.js (lock/revert/save, has_loaded race-condition fix applied proactively from the start), components/business-modelling/BusinessModellingScenarioSection.jsx (three-card UI + history), wired into /business-modelling below the existing live-lever card.

Open questions resolved 2026-09-13 (before build): re-locking is suggested with manual override, not automatic - meaning full history must be kept so a re-lock can be reverted, which also directly serves the CFO gap doc's period-over-period trend need (same underlying "store dated snapshots" mechanism, built once for both purposes). Upside: single scenario only, not multiple variants.

One real bug found and fixed via live testing: Downside initially always showed "Lock a Baseline first" even with a real baseline locked - calculateDownsideAsBreakeven was checking an `available` flag that does NOT survive the storage round-trip (normaliseBaselineSnapshot explicitly rebuilds the snapshot object listing only its real data fields, silently dropping `available` - the same "middle layer drops the field" bug class this whole project has hit repeatedly). Fixed by checking the real underlying data directly instead of a flag that has to stay in sync across a storage boundary.

Live-verified: locked a real Baseline ($630,568 net profit), Downside correctly showed breakeven ($1,869,432) with the right distance message, set a real lever change (Site Crew rate $75->$80/hr) and saved it as Upside, which correctly showed a different, higher total ($712,618) reflecting that specific change.

Old system (businessModellingStorage.js, "Previous scenario tools") deliberately left untouched as the safety net, per this document's own original instruction - not yet retired.
