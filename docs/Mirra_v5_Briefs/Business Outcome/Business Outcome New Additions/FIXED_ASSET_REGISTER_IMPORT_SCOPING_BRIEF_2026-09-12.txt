# Fixed Asset Register Import - Scoping Brief (2026-09-12)

## Why this exists
Today's session built a Balance Sheet import and a Fixed Assets reconciliation comparing Balance Sheet totals against the Assets module's manually-entered purchase_price sum (see CFO_REQUIREMENTS_GAP_2026-09-12.txt Part 1B). That comparison found a genuine $386,245 gap. Investigating why led to a real Xero Fixed Asset Register export being reviewed - and it's clear the Assets module's manually-typed purchase_price values are the likely source of that gap, not a real business problem. This document scopes importing the real Fixed Asset Register to replace manual entry, deferred for a dedicated future session per user decision 2026-09-12 ("this needs to be deferred for the moment but its something we should do").

## What was reviewed
A real Xero Fixed Asset Register export (Assets.xlsx, uploaded 2026-09-12) - NOT the Balance Sheet report, a separate Xero feature entirely (Accounting > Advanced > Fixed Assets, or Accounting > Fixed Assets depending on Xero version - confirmed via web search 2026-09-12, this feature must be explicitly enabled and populated, it is not automatic just because Balance Sheet has asset accounts).

## Real file structure (confirmed 2026-09-12)
Single sheet, 26 columns, 30 asset rows (2 Disposed, 28 Registered) - CORRECTED 2026-09-12, initial scoping miscounted as 29/27; verified precisely when the actual importer was built and tested. Columns:
*AssetName, *AssetNumber, AssetStatus, PurchaseDate, PurchasePrice, AssetType, Description, TrackingCategory1, TrackingOption1, TrackingCategory2, TrackingOption2, SerialNumber, WarrantyExpiry, Book_DepreciationStartDate, Book_CostLimit, Book_ResidualValue, Book_DepreciationMethod, Book_AveragingMethod, Book_Rate, Book_EffectiveLife, Book_OpeningBookAccumulatedDepreciation, Book_BookValue, AccumulatedDepreciation, InvestmentBoost, DepreciationToDate, DisposalDate.

Real AssetType values seen: Motor Vehicles, Plant & Equipment, Office Equipment - these map directly to the Balance Sheet's Fixed Assets subsection categories (confirmed same three categories in the real Balance Sheet export, see xeroBalanceSheetImporter.js).

Real depreciation methods seen: Diminishing Value (most common), Straight Line, Full Depreciation at Purchase.

Key fields for reconciliation: PurchasePrice (gross), Book_BookValue (net, after depreciation), AccumulatedDepreciation - this is the missing data that would let the Fixed Assets reconciliation (built today, currently gross-only) become a genuine net-to-net comparison, using real depreciation instead of the current workaround (see calculateFixedAssetsReconciliation in lib/calculations/balanceSheetCalculations.js).

## What this would unlock
1. Real purchase prices replacing manually-typed guesses in the Assets module - would likely close most or all of the $386,245 gap found today, since that gap is more plausibly manual-entry drift than a real data problem.
2. A true net-to-net Fixed Assets reconciliation using real accumulated depreciation, rather than the gross-only comparison built today as a workaround for the Assets module having zero depreciation tracking.
3. Per-asset depreciation method/rate data the Assets module has never had at all.
4. Names already exist in the register (AssetName, e.g. "Komatsu PC55 Excavator & 3 x Buckets, wide, rock & spade.") that could plausibly match existing Assets module entries (PC55, PC15, etc.) - user's own idea 2026-09-12: bring register assets in as a selectable dropdown list, matched by name, rather than blind re-import.

## Why this is genuinely complex - NOT a quick add, confirmed by user as "a major rejig"

1. **Matching, not blind import.** Existing Assets module entries (PC55, PC15, 2inc Line, etc.) already carry real operational data - hours, rates, finance details - built up over multiple sessions. Register rows need to be matched against these EXISTING entries by name/selection, not appended as new duplicate assets. User's proposed UX: bring register assets in as a dropdown list to select and assign, rather than automatic matching by name string (safer - avoids silent mismatches from slightly different naming, e.g. "Komatsu PC55 Excavator & 3 x Buckets..." in the register vs "PC55" in Assets).

2. **Disposed assets.** 2 of 29 real rows are AssetStatus: "Disposed" (Toshiba Touch Screen FA-0002, Geforce Computer FA-0012) - needs an explicit decision: skip entirely, show as historical/inactive, or something else. Not yet decided.

3. **purchase_price ownership - a real design decision, not yet made.** Does purchase_price become READ-ONLY once sourced from an imported register match (so it can't silently drift from the real Xero data again), or stay manually editable with the register only supplying a starting value? This materially changes the UX and needs a decision before building, not during.

4. **Depreciation flowing into Assets' calculations is genuinely new territory.** The Assets module (hooks/useAssets.js) currently has NO depreciation logic anywhere - confirmed during today's Fixed Assets reconciliation investigation. Bringing in Book_BookValue/AccumulatedDepreciation raises the question of whether Assets' own calculations (true_asset_cost_per_hour, recovery rates, etc.) should ever reflect depreciation - a separate, larger question from just storing the number for reconciliation purposes. NOT scoped - flagged only so it isn't conflated with the simpler "just store the number" version.

## Sizing comparison
Comparable in scope to the Asset Utilisation/Downtime prerequisite from the 2026-09-10/11 sessions, which the user at the time called "major... a huge change in the system." This is not a quick add alongside other work - it changes how purchase_price enters and is trusted within the Assets module, likely touches useAssets.js, assetStorage.js, and needs new UI (the dropdown-matching flow) plus a new importer (following the same pattern as xeroBalanceSheetImporter.js and xeroCogImporter.js - a new lib/imports/xeroFixedAssetRegisterImporter.js).

## Additional scoping (same day, after starting this import) - Depreciation-in-cost decision

Worked through live, using real Komatsu PC55 register data as a concrete test case, before starting the build.

### Real numbers established
PC55: purchase price $72,000, current net book value $42,789.52 (Diminishing Value, 13%, "Full Month" averaging). A year-by-year schedule simulation cross-validated closely against the register's own reported AccumulatedDepreciation figure (within ~1.2% - close enough to confirm the diminishing-value method, small variance likely from Xero's exact month-counting/rounding convention). Estimated current-year depreciation: 13% x $42,789.52 = approximately $5,563/year for this one asset alone - a real, material number, not trivial. Impact if added to PC55's rate (from a real live screenshot, 1,200 recovery hours): asset-only rate would go from ~$12/hr to ~$17/hr (+37%); the group's TOTAL rate (including labour, overhead) would go from $83/hr to ~$88/hr (+6%).

### Why NOT to fold depreciation into true cost/rates unconditionally
- Depreciation is a backward-looking, tax-driven number (based on original purchase price and IRD-set diminishing-value rates), not a direct measure of real wear or real replacement cost.
- A genuinely distorting real example exists in this business's own register: some Office Equipment assets use "Full Depreciation at Purchase" - the ENTIRE cost hits year one, then $0 forever after. If fed unconditionally into rates, this would produce one wildly inflated year followed by an artificially cheap rate for years afterward, with nothing about the asset's real usefulness having changed. PC55 itself (Diminishing Value) doesn't have this problem, but the Assets module needs to handle BOTH depreciation methods safely if this is ever built.
- Depreciation isn't cash leaving the bank, unlike fuel/insurance/maintenance/finance interest (all already in "true cost"). If "true cost" is meant to answer "what does this actually cost me to own and run right now," depreciation sits somewhat outside that definition by design.
- User's real motivation ("otherwise you have to mentally say when I have this much I can [replace it] but we haven't budgeted for it in this tool") is a genuine, real need - but accounting depreciation is an imperfect tool for it. A purpose-built REPLACEMENT PROVISION (expected real replacement cost / expected remaining useful life) would answer "am I setting aside enough to replace this" far more accurately than reusing a tax depreciation formula. Flagged as a genuinely separate, different future feature - not to be conflated with this work. NOT scoped further tonight.

### Decision reached - dual-track approach

**1. Assets module gets a real, per-asset OPTIONAL toggle (default OFF)** - "Include depreciation in true cost" - or similar. When on for a given asset, its depreciation (from the imported register, once that exists) is added into the SAME true_asset_cost_per_hour figure everything downstream already reads.

**2. Deliberately NOT built in Rate Builder.** Confirmed during this scoping: true_asset_cost_per_hour (built in hooks/useAssets.js, exposed on every active_assets row) is the actual shared source Cost Summary, Business Summary, Cost Allocation, AND Rate Builder all independently read downstream. Putting the toggle in Rate Builder alone would mean only Rate Builder ever sees the adjusted figure - every other module would silently disagree with it. Putting the toggle at the Assets module's own core output means every downstream consumer inherits the change automatically, with no rewiring needed anywhere else - matches the same "reuse the engine, don't duplicate it" principle used throughout this session (Business Modelling's live-lever architecture, the EBIT interest join reusing existing asset_group_assignments, etc.).

**3. Business Outcome shows BOTH EBIT and EBITDA, always, regardless of the Assets toggle.** The toggle changes what feeds Rate Builder/Cost Summary/etc. for PRICING purposes. Business Outcome's EBIT/EBITDA display is informational, not a pricing decision, and should show both figures side by side (matching the existing pattern of showing both Real Capacity/Assumed Capacity and Full Cost/Contribution Margin as two honest, differently-framed answers rather than picking one). Once real per-source depreciation exists (via the register import), Business Outcome should compute:
   - EBIT (already built 2026-09-12: net profit + interest)
   - EBITDA (EBIT + depreciation) - a NEW calculation, independent of whatever the per-asset Assets-module toggle is set to for pricing purposes. EBITDA should always use the REAL depreciation figure regardless of whether any given asset has its "include in true cost" toggle on or off.

### What this means for build order, once the register import itself is done
1. Register import brings in real per-asset depreciation data (this document's main scope).
2. Assets module: add the per-asset toggle (default off), wire it into true_asset_cost_per_hour ONLY when on for that asset - additive, opt-in, no default behavior change for any existing user.
3. Business Outcome: extend the existing EBIT calculation (lib/calculations/businessOutcomeEbitCalculations.js) to also compute EBITDA, using real per-source depreciation independently of the Assets toggle setting - both figures always shown together.

Each of these three is meaningfully separable and should be built/verified independently, same live-data-verification discipline used throughout 2026-09-12's session (build, verify against real numbers, commit, before moving to the next piece).

## Confirmed design guarantee (2026-09-12, after /imports hub was built) - no migration, no forced rebuild

User raised a real, important concern before any Assets-module write-back work begins: the Assets module currently has manually-entered (in some cases placeholder/test) data, and not every user will have a Fixed Asset Register at all. Confirmed explicitly:

- purchase_price remains MANUALLY EDITABLE BY DEFAULT for every asset, exactly as today - nothing changes for a user who has no register, or hasn't imported one yet.
- Register-linking (the eventual Assets-module dropdown, pulling a real purchase_price in from an imported /imports register entry) is ENTIRELY OPT-IN, per individual asset - never automatic, never forced.
- purchase_price only becomes read-only for a SPECIFIC asset once that asset is deliberately linked to a register entry by the user (matching the earlier "read only, so you can't invent a number" decision) - every other asset, and every asset before it's linked, stays exactly as flexible as it is today.
- This means NO migration and NO rebuild of existing Assets data is required to ship this feature - it's a purely additive capability sitting alongside the existing manual-entry flow, not a replacement for it.

This is the design guarantee the actual build (Assets-module dropdown, still not built) must honour - confirming it here so a future session doesn't accidentally build a forced-migration version instead.
