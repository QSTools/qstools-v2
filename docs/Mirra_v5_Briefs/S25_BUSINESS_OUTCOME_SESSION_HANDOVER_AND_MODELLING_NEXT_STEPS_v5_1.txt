## 1.2 A real, load-bearing bug found and fixed: `calculateOperatingGroupSplit`
File: `lib/calculations/businessOutcomeAssetSplitCalculations.js`.

The group-level "Labour Charged" figure on the OLD `/recovery-outcome` page (Labour Split /
Asset Split cards) was being recalculated from one flat blended rate × total group hours,
throwing away the already-correct per-staff-type figures the same function had just computed
two lines earlier. This produced a real ~$97,636 discrepancy between "Total Labour Charged"
and Rate Builder's own "Model Capacity" figure, for any group mixing staff types with
different rates (e.g. Foreman: Owner/Director $120/hr + Senior Operator $75/hr).

Fixed: group-level labour charged is now summed from the already-correct per-assignment
figures. Strict rule (confirmed with user): if ANY staff type in a group is missing its own
saved rate, the group's labour-charged total is `null` (unavailable), never a silently
partial sum. After the fix, "Total Labour Charged matches Rate Builder's own Model Capacity
figure" reconciles exactly — confirmed with real numbers, not assumed.

This bug did NOT affect the new `/business-outcome` page's Net Profit figure — that page
runs entirely on a separate hook (`useBusinessOutcomePerSourceRevenue.js`), which already
used correct per-source rates throughout. Only the old page's internal reconciliation
figures were wrong.

## 1.6 The page-wide "Smoothed vs As-Priced" toggle — the big one
This was the deepest design work of the session, and it started as a genuine philosophical
question from the user: does the Real Capacity cascade (Materials floored at $0, labour/
asset groups absorbing the shortfall) accurately represent "who's propping up the business,"
or could a reverse framing ("materials propping up the business") be equally true?

**Resolved with real numbers, not argued in the abstract**: Materials' naive (unsmoothed)
net profit is deeply negative (~-$950k in test data); labour/asset groups collectively have
real, positive naive margin (~+$607k) that's insufficient to fully cover the shortfall. So
"materials propping up the business" is NOT supported by the data — if anything it's the
reverse, and even reversed, the business is still short by the same fixed amount either way.
**Key insight, now documented on the page itself**: the cascade direction never changes the
total — it only changes which line item gets the credit or the blame for a fixed underlying
result.

Given the user's explicit caveat — "we can't unpick this for sure until we run live data"
(real PO/utilisation/monthly P&L reconciliation) — this became a permanent, page-wide toggle
rather than a one-off explanation:

- New state (`smoothing_mode`, "smoothed" | "naive") added to both `/business-outcome` and
  `/recovery-outcome` at the page level.
- Confirmed via live data check that this toggle is ONLY meaningful under Real Capacity —
  Assumed Capacity's own naive and implied figures are already mathematically identical
  (no cascade to undo, since Assumed Capacity only ever applies one flat scale factor).
- Buttons relabeled from technical language ("Smoothed (cross-subsidised)" / "As Priced (no
  smoothing)") to plain language: **"How the Business Runs"** / **"Each Part On Its Own"**,
  with a permanent, always-visible caption explaining what each answers, agreed word-for-word
  with the user before building (see file history for the iteration — landed on framing each
  as answering a different question, not "one is right, one is wrong").
- Card 1 (headline + attention list) now has a genuine naive-mode headline
  (`build_naive_headline()` in `BusinessOutcomePerSourceRevenueCard.jsx`), built from
  `real_capacity.group_real_capacity`'s own `naive_net_profit` field plus materials' naive
  figure — NOT a new calculation, just a different assembly of already-computed, already-
  verified numbers. Verdict language reuses the same `paying_its_way`/`being_carried` keys
  (so existing CSS/styling works), but the underlying number is genuinely different.
- Fixed the naive headline's total to also subtract unassigned cost, so it reconciles
  EXACTLY to the same total as the smoothed view (confirmed: -$369,777 both ways in test
  data) — this was NOT true on the first pass (off by the unassigned amount) until fixed.
- Added a plain-language caption explaining Real vs Assumed Capacity too, landed after
  several iterations: **"Real capacity shares any shortfall out fairly, based on who can
  actually afford to give something up. Assumed capacity shares any shortfall out evenly,
  the same percentage for everyone, regardless of how much margin they have."**

## 1.8 Mechanical/process notes for whoever touches these files next
- `BusinessOutcomePerSourceRevenueCard.jsx` and a couple of others had em-dash/minus-sign
  character corruption occur THREE separate times tonight, every time a plain
  `Get-Content`/`Set-Content -Encoding utf8` round-trip touched the file. Root cause not
  fully diagnosed, but the reliable fix each time was:
  `Get-Content $path -Encoding UTF8` on read, and
  `[System.IO.File]::WriteAllLines($path, $lines, [System.Text.UTF8Encoding]::new($false))`
  on write. Use this pattern for any future edit to this specific file.
- Several PowerShell splice attempts this session had off-by-one indexing bugs (either
  including the original opening/closing brace of a block being replaced, or leaving a
  duplicate). The reliable recovery pattern each time: dump the actual current lines with
  exact 0-based indices via a `for` loop + `Write-Host`, confirm precisely, THEN patch by
  index — never trust a blind multi-line string `.Replace()` on this codebase; whitespace/
  line-ending mismatches silently no-op the replace far more often than they succeed.
- `git config --global core.pager cat` was set partway through the session — without it,
  `git diff`/`git status` open a pager that appears to "hang" until `q` is pressed.

# 5. WHY THIS MATTERS FOR BUSINESS MODELLING — NOT YET DECIDED, FLAGGING THE CONNECTION

**Business Modelling (`/business-modelling`) was NOT touched this session.** Per its own
locked stage handover (`S05_BUSINESS_MODELLING_STAGE_LOCK_HANDOVER_v5.0.txt`), it is
currently stage-locked at "first v5.0 alignment" with an explicit, already-documented
deferred-work list:
- separate minimum model from baseline (currently `minimum_model` just maps to
  `baseline_snapshot` as a placeholder)
- deeper target model controls (target revenue, target margin, target recovery, owner
  profit target)
- connect Business Modelling to Quote Checker and Dashboard outputs
- historical scenario snapshots

Per the system's own locked build order (`00_MIRRA_SYSTEM_PRINCIPLES` /
`02_MIRRA_IMPLEMENTATION_ORDER`), the discipline is: stabilise source → cost → reality →
structure → recovery → rates → **diagnosis (Business Outcome) → modelling (Business
Modelling)**. Business Outcome just had its most substantial, most rigorously bug-tested
session yet — Business Modelling is architecturally the very next stage in that chain.

**The specific connection worth having as a live conversation next session, not decided
here:** tonight's Real Capacity work produced exactly the kind of number Business
Modelling's deferred "minimum model" and "target model" work will eventually need —
`real_capacity.group_real_capacity`'s `naive_net_profit` (what each part earns on its own)
versus `final_net_profit` (what it earns once the business's real cross-subsidy is applied)
is a genuine candidate feed for "what's the gap between where we are and where we need to
be," which is Business Modelling's whole stated purpose ("Business Modelling shows what
happens if the business target changes").

**Also directly relevant**: the S30 doc (referenced in an earlier session's handover, not
re-read in full this session) already flagged that the verification spreadsheet's "Phase 0
scale-factor mechanic" — explicitly NOT built into the live Business Outcome app because
"we aren't doing what-ifs" there — was earmarked as "the reference implementation" if
Business Modelling ever needs baseline-relative what-if scaling. That deferred decision
point is now much closer than it was, given how much of Real Capacity's honest, naive-vs-
smoothed distinction is now live, tested, and trustworthy.

**Recommended concrete first step for next session, if Business Modelling work is chosen
next:** re-read `S05_BUSINESS_MODELLING_BUILD_BRIEF_v5.0.txt` and
`S05_BUSINESS_MODELLING_IMPLEMENTED_STATUS_v5.0.txt` in full (not just this handover's
summary), then have an explicit, un-rushed conversation with the user about whether/how
Business Modelling's minimum/target model separation should consume Business Outcome's
naive vs smoothed Real Capacity figures — this is a genuine design fork of the same
seriousness as tonight's Smoothed/As-Priced toggle decision, and deserves the same
"confirm before building" discipline, not a rushed extrapolation from this note alone.
