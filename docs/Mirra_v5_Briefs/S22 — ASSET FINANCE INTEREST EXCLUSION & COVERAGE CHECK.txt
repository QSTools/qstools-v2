1. THE PROBLEM
--------------------------------------------------------------------

A P&L line can be flagged interest_treatment ===
"contains_asset_finance_interest" (e.g. a bank-fed "Finance Interest"
line of $35,000). Separately, the Assets module independently
calculates total_asset_interest_annual from each financed asset's
own interest figure (e.g. $30,183, built up from live assets).

Both numbers are real. Both come from a legitimate, independent
source. They will not usually match exactly, and the gap between
them is meaningful - but no calculation on the two lump sums alone
can tell which of two very different things the gap means:

  READING A - the gap is genuine, separate business interest (e.g.
  overdraft or business loan interest) that happens to be coded into
  the same P&L "Interest Expense" line as the asset finance interest.
  If true, it is a real overhead cost and belongs in General
  Overheads.

  READING B - Assets is under-counting. The true asset finance
  interest is the full P&L amount, but Assets doesn't show it yet
  because a financed asset is missing, or has a wrong interest rate
  entered. If true, the gap is NOT a separate cost - it belongs
  excluded from General Overheads exactly like the rest of the
  flagged line.

CONCLUSION (unchanged from earlier versions): this is a
missing-information problem, not a formula problem. The fix is to
make the gap VISIBLE at the point where the real information lives -
Assets data entry - and let a human resolve it, instead of guessing
anywhere in General Overheads. Round 2 extended this principle to
Model Reconciliation. Round 3 (this version) extends it again: the
reconciliation page now shows its actual workings, not just a
pass/fail pill, so the visibility principle applies at every level a
person might look.

2. DECISION - FORMULA (General Overheads side) - BUILT, COMMITTED
--------------------------------------------------------------------

KEPT the partial-subtraction formula in
generalOverheadCalculations.js.

For each P&L row flagged contains_asset_finance_interest:

  row_share_of_assets_total =
    (row_amount / flagged_rows_total) * assets_finance_interest_total

  active_amount = max(row_amount - row_share_of_assets_total, 0)

In the confirmed single-flagged-line case this reduces to:
  active_amount = row_amount - assets_finance_interest_total

This is correct, not a compromise - the remainder it leaves in
General Overheads is no longer a silent guess. It is exactly the
same "unmatched" figure the Assets-side card (Section 3) makes
visible, and the same figure the Round 2 Model Reconciliation check
(Section 8) checks for a specific failure mode, and the same figure
the Round 3 "Show the maths" table (Section 14) now shows in a full
per-category breakdown. Formula, card, cross-check, and detail table
are one mechanism, not four.

Confirmed by user directly: "what we have done in general overheads
for the calculation is actually correct - it shouldn't be zero if it
doesn't balance."

10. ROUND 3 (THIS VERSION) - "SHOW THE MATHS" DETAIL LAYER
--------------------------------------------------------------------

### 10.1 Why this exists

The user independently built an external Excel workbook
("Reconsililation_of_Cost_from_FinMirra.xlsx") to manually verify
the whole model's reconciliation - Labour wages/on-costs, Assets'
Interest + Running Costs + Insurance pools, and a per-category P&L
vs Overheads vs Cost Summary table. That workbook surfaced a real,
useful finding along the way (see Section 10.2) but was itself a
duplicate, manually-maintained calculation sitting outside the app -
exactly the kind of "two places computing the same fact" risk this
whole session has been about closing, not opening a new instance of.

Direct quote, on why to build it into the app instead of maintaining
it externally: "it my accounting background I need to see the
numbers laid out so I can see the maths."

DECISION: fold the spreadsheet's detail INTO the existing checks'
breakdown panels, reusing the app's own already-computed numbers -
never a second, parallel calculation. Placed one click deeper than
the existing "Show breakdown" (a new "Show the maths" toggle,
collapsed by default), per explicit user direction: "make sure this
is put on the next layer down... it makes the page interactive but
also we dont want to show all the calcs and confuse the view
straight off when we open the pill." The bridging/proof section of
the spreadsheet (Total Opex - Labour - Asset Finance - Excluded =
Overheads) was deliberately NOT built - once the categories table
below is correct and live, that manual cross-check is redundant; the
system now shows its own working directly.

### 10.2 A real bug surfaced while building this - not in the app

While reviewing the spreadsheet before building this, a live
discrepancy was spotted: the General Overheads module's Finance
Interest line showed only $428 remaining (implying it had excluded
~$35,000), while the Assets module's own confirmed total, in the
same workbook, was $30,183 - a ~$4,817 unexplained gap between what
Overheads actually excluded and what Assets could prove, sitting
exactly where this whole S22 mechanism is meant to catch problems.

Investigated directly in the live app (screenshot review) and
confirmed the root cause: the user had manually typed $30,183 into
the P&L's "Interest Expense" line - the exact figure Assets already
held - specifically "to make things tie out" (user's own words),
and had NOT flagged that line as containing asset finance interest.
This meant General Overheads counted the full amount as an ordinary
cost with zero exclusion, while Assets separately counted its own
$30,183 - a genuine double-count, not a resolved reconciliation.

RESOLUTION: not a code fix - a data-entry correction. Explained why
typing a number to match another module defeats the purpose of
having two independent figures (if they're made to match by
construction, the check can no longer tell you anything). User
corrected the line: flagged as asset finance interest, with the
real P&L amount restored. Once flagged correctly, the module
computed its own genuine match ($30,163) with no manual number
picking - i.e., the Section 2 formula and the Section 3/8 checks all
worked exactly as designed, unprompted, the moment the input was
correct. User confirmed after the fact this was intentional testing:
"no i typed it in to make it match the logic is fine i can change
it. Its just me testing the system." No code changed as a result of
this finding - it is documented here because it is a real,
demonstrated verification of the whole S22 mechanism working
end-to-end, and a useful cautionary example for any future person
tempted to "fix" a reconciliation by editing an input to match.

13. STANDING PRINCIPLES CARRIED FORWARD
--------------------------------------------------------------------

- Never add Assets' asset-finance number into General Overheads to
  backfill an unbooked P&L journal - the Section 2 formula only ever
  subtracts, never adds.
- RECONCILIATION DISCIPLINE: every headline figure must be
  independently re-derivable and checked against a second,
  independently-sourced calculation. Surface disagreements
  explicitly with actual numbers and variance.
- Do not silently resolve a genuine ambiguity in either direction -
  make it visible and let a human decide.
- Distinguish "already resolved by an automatic calculation that has
  already run" from "a genuine open question needing a human
  decision." Only the latter belongs behind an accept/warn mechanism
  (S20) or a red/amber flag.
- NEW this round: when a person wants to independently verify the
  system, build the verification INTO the system, reusing its own
  real numbers - never let a parallel, manually-maintained
  spreadsheet become a second source of truth that can silently
  drift from the app. If detail is needed for trust or audit
  purposes, add a deeper, optional layer inside the existing check,
  not a separate calculation.
- NEW this round: making a number "reconcile" by typing one figure
  to match another (rather than deriving it independently) does not
  verify anything - it removes the only thing that made the check
  meaningful. Documented in Section 10.2 as a real example, not a
  hypothetical.
- Small, isolated fixes to recently-viewed files -> targeted
  -replace patch, verified via Select-String. Larger/uncertain-state
  changes, or files at risk of terminal-paste corruption -> full
  file, delivered as a download or a carefully-verified multi-part
  PowerShell heredoc. (Session-level working convention.)
