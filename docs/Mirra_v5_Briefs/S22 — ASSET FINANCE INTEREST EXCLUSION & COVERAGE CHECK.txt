1. THE PROBLEM
--------------------------------------------------------------------

A P&L line can be flagged interest_treatment ===
"contains_asset_finance_interest" (e.g. a bank-fed "Finance Interest"
line of $35,000). Separately, the Assets module independently
calculates total_asset_interest_annual from each financed asset's
own interest figure (e.g. $30,183, built up from live assets).

Both numbers are real. Both come from a legitimate, independent
source. They will not usually match exactly, and the gap between
them is meaningful — but no calculation on the two lump sums alone
can tell which of two very different things the gap means:

  READING A — the gap is genuine, separate business interest (e.g.
  overdraft or business loan interest) that happens to be coded into
  the same P&L "Interest Expense" line as the asset finance interest.
  If true, it is a real overhead cost and belongs in General
  Overheads.

  READING B — Assets is under-counting. The true asset finance
  interest is the full P&L amount, but Assets doesn't show it yet
  because a financed asset is missing, or has a wrong interest rate
  entered. If true, the gap is NOT a separate cost — it belongs
  excluded from General Overheads exactly like the rest of the
  flagged line.

CONCLUSION (unchanged from v5.0): this is a missing-information
problem, not a formula problem. The fix is to make the gap VISIBLE
at the point where the real information lives — Assets data entry —
and let a human resolve it, instead of guessing anywhere in General
Overheads. Round 2 (Section 8) extends this same principle one level
up, to Model Reconciliation, closing a blind spot where a
misclassified P&L line could hide the same ambiguity from view
entirely.

--------------------------------------------------------------------
2. DECISION — FORMULA (General Overheads side) — BUILT, COMMITTED
--------------------------------------------------------------------

KEPT the partial-subtraction formula in
generalOverheadCalculations.js.

For each P&L row flagged contains_asset_finance_interest:

  row_share_of_assets_total =
    (row_amount / flagged_rows_total) * assets_finance_interest_total

  active_amount = max(row_amount - row_share_of_assets_total, 0)

In the confirmed single-flagged-line case this reduces to:
  active_amount = row_amount - assets_finance_interest_total

This is correct, not a compromise — the remainder it leaves in
General Overheads is no longer a silent guess. It is exactly the
same "unmatched" figure the Assets-side card (Section 3) makes
visible, and the same figure the Round 2 Model Reconciliation check
(Section 8) now also checks for a specific failure mode. Formula,
card, and cross-check are one mechanism, not three.

Confirmed by user directly: "what we have done in general overheads
for the calculation is actually correct — it shouldn't be zero if it
doesn't balance."

Live-tested and confirmed: Finance/Interest category $35,428 -> net
$5,245; General Overheads total $100,684 matches P&L; "General
Overheads vs P&L" benchmark flipped red -> green.

### 3.1 What it is

AssetFinancePnlMatchCard.jsx, in the Assets module, comparing the
flagged P&L asset-finance total to what Assets can actually confirm.

### 3.2 Placement

Assets module page (app/assets/page.jsx), wired to

### 3.3 Fields

  P&L Flagged Total     -> flagged_pnl_total
  Matched to Assets      -> matched_to_assets
  Remaining (unmatched)  -> remaining

All three sourced from calculate_general_overheads()'s existing
output via the useAssets.js useMemo — no duplicate calculation.

### 3.4 Visibility rule

Card renders null (not_applicable) when flagged_pnl_total <= 0 —
i.e. no P&L line is currently flagged.

### 3.5 THREE-STATE STYLING — final, as built (v5.0 specified only
    two states; the third was added in Round 1.5, see Section 6)

  FULLY_MATCHED (remaining ~= 0):
    Neutral styling. "Fully matched." Nothing further needed.

  GAP_PRESENT (remaining > 0, flagged_pnl_total > 0):
    Amber / var(--warning). "Check whether all financed assets are
    entered, or this P&L line includes other interest."

  UNFLAGGED_BUT_ASSETS_HAS_INTEREST (flagged_pnl_total <= 0 AND
  matched_to_assets > 0.01) — added Round 1.5:
    Red / var(--danger) — more severe than a simple gap, because
    General Overheads is counting the FULL P&L amount with no
    exclusion at all while Assets separately holds real interest
    cost: an active double-count, not just an unconfirmed one.
    "Likely misclassified P&L line." / "Check the P&L classification
    for this line - should it include asset finance / interest?"

4. WHAT THIS BRIEF SUPERSEDES
--------------------------------------------------------------------

(Unchanged from v5.0 — kept for history.)

An earlier in-session direction proposed reverting
generalOverheadCalculations.js to full zero-out of flagged rows, on
the reasoning that partial subtraction was an unverifiable guess.
That direction was superseded. The partial-subtraction formula
stays. Full zero-out was independently rejected for a second reason:
it destroys visibility into any real, non-asset interest cost
blended into the same P&L line (Reading A).

8. ROUND 2 — MODEL RECONCILIATION CROSS-CHECK GAP (NEW THIS BRIEF)
--------------------------------------------------------------------

### 8.1 The gap found

User reproduced the same Round 1.5 misclassification scenario, but
one level up, at Model Reconciliation. The Assets card (Section 6)
correctly showed red. But Model Reconciliation showed:
  - General Overheads module: "Fully assigned," no warning.
  - "General Overheads vs P&L overheads benchmark": green, "$0
    Reconciled" (trivially — nothing was excluded on either side).
  - "Asset finance vs P&L asset finance benchmark": green,
    "Expected" (timing-lag styling).

All three misleadingly implied nothing was wrong.

### 8.2 Root cause

A separate, pre-existing reconciliation system (S19-S21 heritage) in
reconciliationRules.js computes its own view, independent of the
Round 1 General Overheads formula:
  asset_finance_interest_covered_amount =
    Math.min(excluded_asset_finance_interest_total,
             total_asset_interest_annual)

getAssetFinanceVarianceCheck only used the strict coverage check
(Section 8.4 below) when something was actively flagged
(excluded_asset_finance_interest_total > 0). With nothing flagged,
it fell back to a timing-aware check that treats "Assets ahead of
P&L" as an unposted journal, not an error — correct when no interest
line exists yet, but wrong when a line exists, was actively
reviewed, and was marked "does not contain asset finance interest."
The system had no way to distinguish "not yet reviewed" from
"reviewed and rejected."

### 8.3 Fix — misclassification check at Model Reconciliation level

New function getAssetFinanceMisclassificationCheck(), returning
status: "warn", is_warning: true, is_timing_expected: false.

getAssetFinanceVarianceCheck extended with a
reviewed_non_asset_finance_interest_total param (sourced from
Section 7's new P&L calculation field). New branch: if
reviewed_non_asset_finance_interest_total > 0 (a genuine reviewed
rejection has happened) AND total_asset_interest_annual exceeds
tolerance, returns the misclassification check instead of falling
through to the timing-aware default.

Live-tested and confirmed by user: the benchmark tile now correctly
shows a warning instead of "Expected" for this scenario.

### 8.4 Fix — the healthy "Covered" state was ALSO misleading, for a
    different reason (this is the design discussion this brief
    closes out)

Separately, even in the CORRECT/healthy state (line properly
flagged, e.g. $4,817 gap between P&L $35,000 and Assets $30,183),
getAssetFinanceCoverageCheck's "Covered" tile showed a green pill
with a bare -$4,817 sitting next to it at the collapsed/headline
level. User's objection, refined over several turns:

  - A green pill next to a signed dollar figure reads as a *pending
    variance to chase*, not a *resolved fact* — regardless of what
    the expandable detail text underneath says. Wording alone can't
    fix a perception problem created by the number's presence and
    position.
  - The critical realisation (from the user, transcribed live):
    "the four thousand eight hundred and seventeen is actually now
    in the General Overheads" — i.e. this is NOT an open item at
    all. The Round 1/2 formula (Section 2) has ALREADY moved that
    remainder into General Overheads, automatically, as part of the
    normal calculation that already ran. There is nothing pending
    and nothing for a human to accept or resolve — the module has
    already made its decision.
  - This ruled out Claude's first proposal (route this into the S20
    manual-accept mechanism, matching the Assets card's amber/accept
    pattern) — S20 accept is for genuine open residual variances
    needing a human decision. This is not one. Routing an
    already-resolved, automatically-applied allocation through an
    "accept" flow would incorrectly imply a decision is still
    outstanding.
  - CONCLUSION (final, as built): status stays "covered" (not
    "warn"), NOT routed through S20. Two things change instead:
      (a) WORDING — message rewritten from "...this has not been
          confirmed, check before trusting this figure" to "...has
          already been carried into General Overheads as other
          interest cost - this is already accounted for, nothing
          further to do here."
      (b) DISPLAY — the headline dollar figure is hidden entirely
          for any check with status === "covered" (currently unique
          to this one check), in
          ModuleReconciliationSummaryCard.jsx's ComponentRow. Only
          the pill and "Show breakdown" remain at a glance; the
          number and its explanation live inside the expanded detail
          only, where context exists to interpret it correctly.

  Asymmetry confirmed explicitly by user and preserved in the build:
  this treatment applies ONLY when Assets <= P&L (the remainder has
  a legitimate home in General Overheads, by design, already
  applied). When Assets > P&L (module claims MORE interest than
  P&L accounts for), that direction has no such home to fall into —
  it remains a real, un-absorbed gap, correctly kept as status:
  "warn" with the dollar figure shown and the existing S20 accept
  flow available, unchanged from pre-Round-2 behaviour.

10. STANDING PRINCIPLES CARRIED FORWARD
--------------------------------------------------------------------

- Never add Assets' asset-finance number into General Overheads to
  backfill an unbooked P&L journal — the Section 2 formula only ever
  subtracts, never adds.
- RECONCILIATION DISCIPLINE: every headline figure must be
  independently re-derivable and checked against a second,
  independently-sourced calculation. Surface disagreements
  explicitly with actual numbers and variance.
- Do not silently resolve a genuine ambiguity in either direction —
  make it visible and let a human decide.
- NEW this round: distinguish "already resolved by an automatic
  calculation that has already run" from "a genuine open question
  needing a human decision." Only the latter belongs behind an
  accept/warn mechanism (S20) or a red/amber flag. Surfacing an
  already-applied, automatic allocation as if it were still pending
  is its own kind of misleading — the fix in Section 8.4 exists
  specifically because "make it visible" and "imply it's unresolved"
  are not the same thing, and conflating them caused three rounds of
  user confusion before landing on the distinction above.
- Small, isolated fixes to recently-viewed files -> targeted
  -replace patch, verified via Select-String. Larger/uncertain-state
  changes -> full file. (Session-level working convention.)
