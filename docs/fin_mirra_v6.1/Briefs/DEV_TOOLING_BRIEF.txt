1. PURPOSE
===============================================================================
The slow, expensive part of building Mirra is not writing code, it is (a) Claude finding what touches what by searching and reading big files, (b) the terminal runs (seed regression 10 to 15 minutes, mainly the 1,000 staff seed) and the long outputs pasted back, and (c) briefs so large that every chat spends tokens reading or writing them. This brief covers small read-only tools that cut those three costs and catch the recurring dropped-field bug class (conventions rule 6b) earlier. Owner: "build this correctly right from the very beginning" and "I don't want to wait till I feel the pain".
Owner context: a YouTube plugin (name not confirmed, something like Graphify) draws a 3D graph of a repo. The owner and Claude judged it to be packaging around a plain list of connections. Decision: build our own, no dependency, no subscription, no visualiser.

4. THE PIECES (what each must do, and how it is checked)
===============================================================================
T0  LOOK FIRST (read-only, start of chat 1, no building). (a) Read one real regression output and one real paste-back to decide how much to cut. (b) Read the Py\stress_test harness: per-seed run times, and whether seeds can run in parallel (NOT VERIFIED: no one has read the harness for this). (c) Note which audit scripts already do part of this (extract_calc_map.py already scans functions with line numbers; bm7_a to bm7_f already map storage readers and writers for the BM-7 audit, BM brief Addendum 7) and REUSE their code rather than write a second scanner.
T1  IMPORT GRAPH. Scans the repo source (app, components, hooks, lib, plus the scripts folders if cheap) and records, per file, which files it imports, including re-exports (export ... from), require, and dynamic import(). Must resolve path aliases from the project config (NOT VERIFIED which aliases exist; check jsconfig or tsconfig first) and barrel (index) files. Output two files from the SAME scan: a JSON master (for the future AI layer and scripts) and a flat text file, one line per connection, for Claude to search by name (example shape: "hooks/useCostAllocation.js imports lib/storage/modelDiffs.js"). Claude never reads the text file whole: it searches a name and gets only the matching lines (one hop out from the files a task touches).
T2  STORAGE KEY MAP. From the same scan: for every localStorage key, which files read it and which write it, including reads that go through the storage helpers and the registry codes (m01, m23, m24 and so on). Dynamic keys built by string concatenation are listed as "dynamic" with the file, never guessed. Used for: dropped-field bugs (a layer that rebuilds an object and drops a field), the lever batch merge points, and the R6 database migration (a reliable list of what reads and writes each key).
T3  CALC MAP DRIFT CHECK. Compares the function names and line hints in CALCULATION_MAP_v6_0.txt with the code and prints the entries that no longer match. Extends the existing extract_calc_map.py approach; it only reports.
T4  ONE-COMMAND PRE-COMMIT CHECK plus SUMMARY OUTPUT. One command runs: git status summary, the build, the unit tests (all, or those for changed files), the audit scripts (trace coverage, brief currency, project knowledge sync, graph fresh, calc map drift), and prints ONE line per step and a single PASS or FAIL, with detail only for failures. It must REFUSE to build while a dev or production server is running on :3000, :3004 or :3005 (conventions rule 14: a build while npm run dev runs corrupts .next) and say so. It only runs things; it changes no source. The regression harness gets a matching short mode: one line per seed (PASS or FAIL with the counts) and full detail only on a failure.
T5  BRIEF SPLIT AND ADDENDUM INDEX. For each oversized brief (BUSINESS_MODELLING_BRIEF is 346,969 bytes at 2026-11-09; check the others): a short CURRENT-STATE brief (live rules, open items, status, the last few addenda) and an ARCHIVE file holding the older addenda word for word (docs\Archive\ or beside the brief, to be decided), plus an INDEX with one line per addendum: number, date, topic, status (current or superseded). Claude reads the index, then opens only the addendum it needs. The existing rule "never create a second brief for a module" (PROJECT_MAP section 1) is kept: the archive is history, not a second brief. Project knowledge holds the current brief and the index; the archive stays in the repo and is staged on demand (decide whether it also goes in project knowledge for search). Rule 11 (append a dated addendum) still applies to the current brief.
T6  SKILL. After T1 and T2 exist, write a skill that says: look things up in the graph by name, never load it whole; check the graph is fresh; regenerate with the one command at the end of any chat that changed code. One line added to the session start skill to check graph freshness. (Skills are saved through the review card; the owner saves them.)
