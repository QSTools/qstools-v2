===============================================================================
1. PURPOSE
===============================================================================
Business Modelling lets the owner change genuine decisions (overheads, charge-out rates, unit rates, markup) and
see the effect on net profit against TODAY's real position. The method (owner, confirmed): walk down the chain in
order - overheads first (they move every floor), then labour rates, then assets and materials - and see the result.
Every source is shown against three markers:
  FLOOR   breakeven (full true cost + non-productive share per covered hour; 0% for materials)
  START   current achieved rate from Business Outcome (View A)
  CEILING the entered rate x the hours it can cover (not a cap - a ceiling can sit below the floor)

===============================================================================
2. OWNS / DOES NOT OWN
===============================================================================
OWNS: lever state (qs_tools_business_modelling_levers_v1); the today / modelled / change display; source rows built
from per_source; the additive model.
DOES NOT OWN: any business calculation - it reads Business Outcome's per_source (and General Overheads' grouped rows,
read-only). Never writes to a source module. Never overrides Model Readiness. Never infers missing source truth.

===============================================================================
3. RULES (do not break)
===============================================================================
R1  TODAY is never mutated. With no levers set, modelled == today exactly.
R2  Revenue, net profit and cash are consequences, never levers. Genuine levers: charge-out rates, unit rates,
    markup, undistributed overhead lines, staffing / hours, financing. NEVER levers: employer KiwiSaver (hard-locked),
    ESCT, ACC (constrained to a small legislated band at most), insurance premiums, market fuel prices.
R3  Touch one lever -> only that source changes; every other source stays at today's achieved figure; total = today's
    real total + the sum of the effects (owner, 09-18, reconfirmed). Effect = (target - START) x basis (cost rows
    inverted). Basis = COVERED hours, never seat hours; materials basis = COGS / 100.
R4  Display: keep TODAY fixed, show MODELLED beside it and the CHANGE (Q1).
R5  Overhead levers touch only the UNDISTRIBUTED General Overheads pool, line by line - never a line already
    distributed to an asset (that would corrupt Cost Allocation).
R6  Labour levers are per staff type; asset levers per unit. An asset-driven unit is ONE lever - the all-in unit rate;
    its labour rows show "in_unit_rate", not leverable; the machine share is shown live via Rate Builder's own
    calculate_net_asset_rate. The all-in guide is not a cap.
R7  Materials: START 0%, FLOOR 0%, CEILING = Rate Builder markup (View A floors materials; owner D-VIEW).
R8  Shortfall distribution stays PRO-RATA (order-independent), not a waterfall.
R9  Row labels are "unit / staff type" (name trap: working unit "Site Crew" vs staff type "Site Crew").

ADDENDUM 2 (2026-10-27) - MODELLING MODE DESIGN DECISIONS  [DECISION: design only, nothing built, no code touched]
Source: owner voice session 2026-10-25, written up 2026-10-27. Refines Section 9 and the 2026-10-16 redesign brief
(Future_Build). Tags: DECISION = owner stated or confirmed it; PROPOSED = suggested in the session, not confirmed;
OPEN = unresolved.

TERMS (use these names from here on)
  REAL DATA   Layer A. What the pages hold in normal mode. Edited until the business is set up correctly.
  BASELINE    Layer B. The locked snapshot of the settled business - what the business is doing now and has done.
  MODELLED    The owner's changes to the baseline, saved on their own layer as differences. Tier 1: fixing the business
              you have. (Replaces the freely discardable Layer C scratch overlay for Tier 1: it persists.)
  SCENARIO    Structural what-ifs on top of the modelled layer. Tier 3: add or remove staff or assets.
  Stack: BASELINE, then MODELLED on top, then SCENARIO on top. Real data is never touched by any of them.

 1. [DECISION] The baseline is never written to by modelling. All modelling lives on its own separate layer. Modelling
    never writes back to the baseline or to real data; a real change is made on the actual page in normal mode.
    Whether a modelled change can be promoted into real data is NOT decided (2026-10-16 brief, open question 1).
 2. [DECISION] Reuse the real pages. General Overheads, Labour, Assets, Rate Builder and the rest run in modelling mode
    against a copy of the baseline, with levers to change numbers. There is no separate modelling inputs page. This is
    the Section 9 mechanism, now confirmed by the owner.
 3. [DECISION] ONE universal toggle switches the whole tool between baseline mode and modelling mode. Not per page.
    Reason: the owner never wants baseline data entered into the modelled layer by accident, or the reverse; keep it
    simple. Check at build: in modelling mode nothing reaches the real or baseline keys; in baseline mode nothing
    reaches the modelled key.
 4. [DECISION, route fate OPEN] Business Outcome gets a baseline view / modelled view toggle: same layout, same
    figures, same identity checks; only which copy of the inputs it reads changes. The owner prefers this to a big
    separate Business Modelling results page (one place for results, one set of calculations to verify). Whether
    app/business-modelling stays as a thin page (toggle, lock / unlock, today-versus-modelled comparison) or is retired
    in favour of Business Outcome is not settled. The old lever page is retired either way (Section 9).
 5. [DECISION] Locking the baseline is an explicit commit of a snapshot, saved only when everything is aligned: all
    flags cleared and reconciliation passing (Model Readiness). Getting the tool to that point is the owner's work
    through the pages, with AI-assisted setup helping because it is complicated. After the commit the baseline cannot
    be changed by modelling.
 6. [DECISION] Editing a locked baseline is a deliberate act (an unlock step) for fixing a mistake, never an accident.
    [PROPOSED] When the baseline is unlocked and changed, the modelled layer shows a warning that its starting point
    moved (so the owner can see what changed). Wording and mechanism not designed.
 7. [DECISION] Modelled changes carry over a baseline correction; they are not cleared. So modelled changes are stored
    as DIFFERENCES from the baseline (for example "this overhead line -$X" or "this rate +$Y"), never as full copies of
    the final value. Result: correct one baseline number and BOTH views update, with the modelled adjustments still
    sitting on top. Fixing the same mistake twice must never be needed.
 8. [DECISION] A difference whose target no longer exists or no longer has anything to reduce (the owner's example:
    a subscription reduced in the model, then deleted from the baseline) resolves to zero. It never goes negative and
    never throws. [PROPOSED] It carries a visible flag, e.g. "this change no longer applies because the line was
    removed", so the owner can see why a number moved.
 9. [DECISION] Scenarios sit on top of the MODELLED layer, not on the bare baseline. The owner models the business as
    they want it, then asks future questions of THAT business: can I afford a new staff member, what does a new digger
    do, what does a non-productive asset do. A scenario adds or removes rows (Section 9, Tier 3), so it is a stored set
    of added / removed rows plus their inputs, not just changed values. This SUPERSEDES the 2026-10-16 rule that Tier 3
    comparisons run against Layer B. The honest limit still stands and is shown on screen: a scenario shows cost burden
    and floor rate; it cannot invent the revenue or work that would pay for it.
10. [OPEN] Scenario storage and comparison. The 2026-10-23 AI brief (Section 8.5) describes a scenario as a throwaway
    copy; storing it as a small set of rows would let several sit side by side. Not decided: keep several or one at a
    time; compare scenarios against each other or only against the modelled layer; any cap. (BM-9)
11. [DECISION] No pre-modelling from pooled or "standard practice" data. The idea of gathering background metrics from
    users to say what a typical fix looks like was rejected by the owner ("a terrible idea, scratch that"). Read with
    the AI brief's rule 7.2: Mirra shows what a lever does in THIS business and never says what to do or what other
    businesses do. Cross-business benchmarking stays parked behind the lawyer-review gate. (Interpretation note: the
    owner's reply was a "yes" followed by "scratch that"; recorded as rejecting the pooled-metric idea. Confirm.)
12. [OPEN] First step is still the engine purity audit (BM-7): read-only, not yet run. The owner chose to settle what is
    being built first. New storage keys (baseline, modelled, mode flag, scenarios) are a first-time storage schema and
    need a separate confirmation before building, with has_loaded guards from the first commit (conventions rule 8) and
    selectors that spread rather than rebuild objects (bug class 6b).
13. AI relationship (from the 2026-10-23 brief, Section 8): any assistant on target modelling waits until the lever
    layer is settled and verified by hand; it proposes within limits taken from the business's own baseline and the owner
    confirms. Per-source targets and the cross-subsidy-shrinking-to-zero measure belong to that brief.

WHAT CARRIES OVER FROM THE EXISTING ENGINE: rules R1-R9 describe the current lever engine, which R3 retires. What
survives as acceptance checks: no changes == today, own START rate == zero effect, effects additive. R3 "touch one
lever, only that source changes" is replaced by "the real chain recomputes on the changed copy".

ACCEPTANCE ADDITIONS FOR THE R3 BUILD (figures to be fixed at the audit from the live baseline, not invented here)
  - Modelling mode with no differences reproduces the baseline net profit exactly.
  - Change one number in the baseline (after unlock): baseline view and modelled view both move, and the modelled
    differences are unchanged.
  - Delete a line that has a modelled difference: that difference resolves to zero, flagged, no negative, no error.
  - Real data (Layer A) and the locked baseline are byte-identical before and after any modelling session.
  - Removing then re-adding the same asset or staff member in a scenario returns to the modelled numbers.
  - Scenario on top of modelled: with an empty scenario the result equals the modelled view.
