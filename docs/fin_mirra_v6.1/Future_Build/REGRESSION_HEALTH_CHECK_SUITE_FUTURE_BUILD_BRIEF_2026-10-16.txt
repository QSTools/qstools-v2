1. WHY THIS DOCUMENT EXISTS
===============================================================================
The owner's stated requirement is that the tool be 100 percent accurate, and his stated fear is what happens when a
calculation or a storage shape has to change after real data exists: the data becomes too tangled to fix and the
database is wiped and rebuilt (his experience with Power Query and replacing values by hand). This brief records the
answer agreed in the session: a permanent suite that proves correctness before any change can reach real data, plus
a short list of data-protection rules. It also records the owner's idea that the suite run on a schedule, which is
ordinary industry practice (regression testing) and not a special measure.
This suite cannot make a live system risk-free. It removes one failure mode: silent drift in calculations that
is discovered only after real users hold the numbers.

3. WHAT IT RUNS AGAINST
===============================================================================
  - Synthetic seeded data on an ISOLATED instance (the smoke test pattern: localhost:3004, its own localStorage
    origin; later a dedicated test tenant on a test database). NEVER live user data.
  - Because it never touches real data, it cannot corrupt production, and 1,000 real users do not make the suite
    itself more expensive. Server and concurrency load is a separate concern, covered by the later step 6 test.
  - Proposed guard (not decided): the suite refuses to run against any dataset that is not flagged as synthetic.

===============================================================================

5. PROTECTING REAL DATA (a separate mechanism from the suite)
===============================================================================
  The suite protects the CALCULATIONS. These rules protect the DATA:
  - Additive, versioned migrations. Nothing destructive in place.
  - A backup before every schema or logic change that touches stored data.
  - One source of truth: a stored number is always written by the same calculation code the app uses (server side
    after steps R6), never hand-patched and never re-derived somewhere else.
  - A field's meaning changes only across full releases, never silently mid-flight.
  - A change reaches the real database only after it has passed this suite on synthetic data.
  - Every calculation node is stored (launch Addendum 1, A4), so if a number looks wrong it can be traced to the node
    where it diverged instead of being found as a wrong headline figure with no trail.

===============================================================================
6. STEP 1c AND STEP 6 ARE NOT DUPLICATED WORK
===============================================================================
  Step 1c (R2) proves correctness once, client side, with no server. Step 6 (R9) re-runs the same pack against the
  server-migrated version (cheap, and it catches migration bugs) and adds one genuinely new dimension that cannot
  exist before migration: server load and concurrency. Owner confirmed the distinction.

===============================================================================
7. ADDITIONS WHEN THE DATABASE EXISTS
===============================================================================
  Two launch-gate tests join the suite after R6 (launch Addendum 1, A4):
    (a) full-node storage performance at about 1,000 businesses: write volume and query speed, measured;
    (b) a deliberate tenant-isolation breach attempt: query as one business and confirm no row of another is reachable.
  The k6-style concurrency and load test against a deployed environment is separate background work and not a launch
  blocker.

===============================================================================
8. ACCEPTANCE CRITERIA (PROPOSED, owner to confirm; no figures invented)
===============================================================================
  - One command runs pieces 1 to 4 and prints one overall PASS or FAIL, with non-zero exit on any failure.
  - Expected values come from the independent script written from CALCULATION_MAP_v6_0.txt, never from the app's own
    code. A suite that checks the app against itself proves nothing.
  - Known-bad check: feed the suite a seed with one deliberately wrong value and confirm it FAILS. A suite that has
    never been seen to fail is not trusted.
  - The same seed is run before and after every migration and must give identical node values.
  - Every figure that has a trace node (the definition of done) is covered by at least one expected value.
  - Results are written to a dated file so a change in result between runs is visible.
