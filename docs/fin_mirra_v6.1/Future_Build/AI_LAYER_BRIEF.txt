1. WHY THERE IS AN AI LAYER
===============================================================================
 - [DECISION] Early viewers said the tool is "too complicated to understand and use". The calculation chain cannot
   be simplified without becoming wrong. So the complexity stays in the engine and the EXPERIENCE is simplified by
   the UI tidy-up (R5) and the AI layer (R7). That is why the AI layer is inside the launch bar, not a nice extra.
   (POST_LAUNCH_VISION s2; LAUNCH A2)
 - [DECISION] The core tool is deterministic: same inputs, same outputs, verified, not trusted. It must never become
   "AI does the maths". The AI layer sits beside it and explains. (POST_LAUNCH_VISION s3)

===============================================================================
2. THE AI SURFACES (one layer, four places users meet it)
===============================================================================
  A. LANDING-PAGE FIN      Pre-login, voice. Explains what Mirra does and invites the visitor to start. (Section 3)
  B. SETUP COACHING        Inside the tool. Interviews the owner and gets the right numbers into the right boxes.
                           (Section 4)
  C. EXPLAINER AGENT       Inside the tool. Reads stored, already-calculated numbers and explains them. (Section 5)
  D. LATER EXTENSIONS      Target-modelling assistant, weekly digest / drift, outside-the-app agent surface,
                           invoice-matching suggestions. (Sections 6 and 7)
  B and C ship TOGETHER as R7, inside the launch bar. A is not on the build order yet. D is post-launch.

3. LANDING-PAGE FIN (pre-login)
===============================================================================
Behaviour spec: Fin_landing_page_guardrails_v0_2.json (2026-10-27; supersedes v0.1). The JSON is the source of
truth for wording; this section records the decisions behind it.

 3.1 [DECISION] Role: a gentle salesperson, not an analyst. Only positive. Slowly reveals what the tool can do for
     the visitor. Replies 2-4 sentences: warm, enough to build the picture, never a pitch dump, never clipped.
 3.2 [DECISION] Structured flow, so Fin cannot wander: opener -> what we do -> live worked example -> what else ->
     how the model comes together -> setting one up. Side questions are answered within the rules, then Fin steers
     back to the next stage.
 3.3 [DECISION] Opener: "Welcome to FinMirra, I'm Fin. We're a digital CFO platform that helps you investigate how
     your business is actually running. Would you like me to explain a little more about what we do?"
 3.4 [DECISION] Core explanation: baseline (how the business runs today, from the P&L) -> model (how it needs to run
     to be profitable, in Model Your Business) -> live data checked against both, refreshed every month. The model
     gets smarter the more of the business it sees.
 3.5 [DECISION] Hook: a live worked example from two numbers (hourly rate, hours per week), using the NZ entitlement
     of two paid 10-minute breaks per 8-hour day. Check values at $50/hr, 40 hrs/wk: about 87 hours a year, about
     $4,300 a year, cost per productive hour about $52.17. Lead-in: "Would you like me to show you a quick example
     of what we can do?" Results stated neutrally; then a soft landing, no push.
 3.6 [DECISION] Hard rules: never criticise or imply a gap or mistake; never generalise ("most owners"); never refer
     to, compare with or put down any other tool or company; never estimate a number about the visitor's business
     beyond the worked example; never ask for more than a chat can use.
 3.7 [DECISION] Never interrupt. A pause is part of the same thought. Prompt wording alone cannot fix this: the voice
     platform's end-of-speech silence threshold must also be raised (target at least 1-2 seconds). Owner benchmark
     from testing: Claude interrupts most; Copilot over-explains; ChatGPT was best of the three.
 3.8 [DECISION] "Simple in hindsight, invisible beforehand" is static page text only, never spoken (spoken, it
     implies the visitor missed something). "We mirror your business back to you" may be spoken.
 3.9 [DECISION] Quick Start is removed from Fin's flow for now. [PROPOSED, product idea] Quick Start could later
     carry the same paid-breaks hook as a two-input tool.
 3.10 [OPEN] Fin must not claim quote checking. DISCREPANCY TO RESOLVE: the owner said on 2026-10-27 that quote
     checking is "not built", but QUOTE_ENGINE_BRIEF records Quote Engine and Quote Checker pages built in
     v3.7-v5.0 and carried forward, NOT VERIFIED in v6.x. Decide whether the owner meant a different feature
     (checking quotes against the live model) or whether the existing pages should be retired or verified. Until
     then, Fin does not mention quotes.
 3.11 [OPEN] Closing invitation after the setup stage (into Model Your Business): wording not agreed.
 3.12 [OPEN] RULE CONFLICT: the worked example is a calculation shown to the visitor, but the standing rule is that AI
     never produces a number the user treats as true (Section 8.1). [PROPOSED] Resolve by running the example in
     plain deterministic code (a fixed formula with its own check values and, ideally, the tool's own labour
     break settings), with Fin only reading out the result. Fin does no arithmetic of its own.
 3.13 [OPEN] The example uses 52 working weeks and does not remove leave or public holidays. Keep it simple or adjust.

5. EXPLAINER AGENT (R7, part 2)
===============================================================================
 5.1 [DECISION] Read and explain, never compute. It fetches stored, already-calculated outcomes and explains,
     compares and points out patterns in plain language. "Otherwise, what was the point in us building everything."
     (STRESS D-8, s7.1)
 5.2 [DECISION] It calls a fixed set of defined tool functions (e.g. a business's Business Outcome summary, a staff
     member's true cost, current Cost Allocation groups). Each returns structured JSON from the stored tables,
     scoped to the one business by tenant isolation. It never writes its own database queries. (STRESS 7.2)
 5.3 [DECISION] Every calculation node is stored in the database, so the agent can answer any question about any
     number. Node shape is therefore part of the schema. (LAUNCH A4)
 5.4 [DECISION] Hand-off point: Business Outcome and Business Modelling, the most complex screens. (LAUNCH R7)
 5.5 [DECISION, mechanism PROPOSED] What-ifs are the one exception to "never compute": allowed only if clearly
     labelled as not actual, and proposed to run through Business Modelling's own calculation, with the agent
     explaining the result. No hypothetical figure is ever shown as an actual. (STRESS 7.3)
 5.6 [DECISION] Explains, never advises. Mirra shows what a lever does in THIS business; never what to do, never
     what other businesses do. Diagnosis wording states the arithmetic only. (BM decision 11; BM Addendum 3 item 4;
     23 Oct brief rule 7.2 as quoted)
 5.7 [PROPOSED, owner has not commented] Log what was asked and what data was returned, for trust and for client
     compliance requests. (STRESS 7.4)
 5.8 Dependencies: the database with stored outputs (R6), tenant isolation, result_interpretation text on nodes,
     stable screens (R5).
 5.9 [DECIDED 2026-10-28, Addendum 2 item 11; was OPEN] Do nodes need plain-language text stored alongside their
     values? Decide when nodes are built, not after.
     (LAUNCH A3)

7. DATA, PRIVACY AND SECURITY
===============================================================================
 7.1 [DECISION] Baseline security is settled and non-negotiable: in transit (TLS), at rest, and row-level tenant
     isolation enforced in the database from day one. One business must never see another's data; a deliberate
     breach attempt must fail before launch. (STRESS 5.2; LAUNCH A2, A4)
 7.2 [DECISION, 2026-10-27] Business data will be encrypted. Fin may say so publicly. [OPEN] Which fields get
     field-level encryption on top of the baseline. Starting advice (not final): personally identifying fields
     (staff names, contact details, possibly pay tied to a named person); calculated figures rely on the baseline
     because Cost Allocation and Rate Builder query them in bulk. The list goes to someone experienced in securing
     financial SaaS data before the schema is fixed at R6. (LAUNCH A4)
 7.3 [DECISION, 2026-10-27] No one inside FinMirra can browse a client business's data. Account details (e.g.
     business name) are held to run the account.
 7.4 [DECISION, 2026-10-27] A written data collection and privacy policy is required before any AI surface fields
     data questions live. Not written. Until it exists Fin says only: business financial information stays private
     and encrypted; a full policy is on its way.
 7.5 [PROPOSED, 2026-10-27, for the policy] Generic, non-identifying signals that may be used to improve the product:
     - the kinds of questions people ask Fin and the explainer
     - where people get stuck or drop off in setup; how long setup takes; which features get used
     - location at region level (e.g. NZ vs Australia rules)
     - invoice line-item DESCRIPTIONS only (never quantities, prices, supplier or customer identity) to improve the
       generic invoice-matching system
     Owner position: "we effectively don't collect any personal information" for improvement purposes.
 7.6 [DECISION] Not the same thing as benchmarking. Pooled "typical business" metrics were rejected (BM decision 11).
     Cross-client benchmarking (anonymised bands) stays parked behind the LEGAL GATE in AI_STRATEGY A.7, and if ever
     built needs its own stored consent flag (scoped to anonymised ratios, never raw data, never model training).
     The policy must keep product-improvement signals and benchmarking clearly separate.
 7.7 [OPEN] What data is sent to an outside AI service for the explainer and coaching, the consent wording, and the
     per-use cost. (Setup brief Q4)

8. STANDING RULES FOR EVERY AI SURFACE
===============================================================================
 8.1 AI never produces a number the user treats as true. Numbers come from the deterministic engine, stored and
     traceable. (STRESS D-8; SUPPLIER s2)
 8.2 What-ifs are labelled as not actual and run through the tool's own calculation.
 8.3 Explain, never advise; this business only; no comparison with other businesses or other tools.
 8.4 Never claim a feature that is not built. Not built today: native timekeeping, purchase orders, work orders,
     Xero write-back, any live feed other than the accounting P&L and balance sheet. (Fin v0.2; LAUNCH R8)
 8.5 Read through fixed, tenant-scoped functions; never free-form queries.
 8.6 A human is the buffer: suggestions are confirmed by a person before they become data. (AI_STRATEGY C3, M2)
 8.7 Voice surfaces never interrupt (3.7).

A. IN-APP FIN: WHAT THE PROOF OF CONCEPT AND RACI PLAN ADD (feeds Sections 4, 5 and Q-3)
 1.1 [PoC] Fin answers only from the JSON it is given. One payload answered many different questions, so Fin is not
     tied to buttons or canned reports. Answer quality is proportional to the structured context supplied. Fin never
     calculates: Mirra calculates, Fin explains what happened, why, what is missing and the business impact.
 1.2 [PROPOSED] Answer to Q-3. A read-only, in-page Fin needs no database. The page's output-contract hooks build the
     payload in the browser, POST it to a server route that holds the model key, and show the reply. That is what the
     PoC did with pasted page JSON. Stored nodes (5.3) are needed for history and a scheduled agent, not for explaining
     the page you are looking at. Condition: the model key stays server-side. The headless question (AI_STRATEGY G1a,
     can the chain run outside a browser) then only affects a scheduled agent, not this first cut.
 1.3 [PROPOSED] Payload shape (RACI Phase 2): user_context, page_context, business_context, verified_outputs, findings[],
     missing_data[], agent_rules, traceability. Rule: verified outputs and semantic labels go out; formulas and mechanism
     documents (CALCULATION_MAP, VARIABLE_TRACKER, trace briefs) never do. This answers AI_STRATEGY R1 for Fin: the
     question of what leaves the app is live the moment Fin's route exists. The landing-page JSON is unaffected
     because it holds public pitch content only.
 1.4 [PROPOSED] The PoC sent employee names and salaries because richer context gave better answers. That conflicts with
     Section 7. Proposed resolution: richer context comes from verified outputs with semantic labels, and the payload
     uses role/type labels and pool names by default ("Operator / Delivery Staff"). Individual names only if the owner
     decides so (Q-17). Feeds the field-level encryption list (7.2) and the outside-AI data question (7.7).
 1.5 [PROPOSED] Build the payload from the calculation trace layer plus the output contracts, not from raw module state.
     [FINDING] The 2026-09-29 trace snapshot has 100 nodes and 108 edges, no duplicate ids, no missing endpoints. Each
     node already carries node_id, display_label, module_name, is_root_input, value_format, implementation_status,
     inputs and resolved_value. That fits 4.2 and 5.3. Cost Allocation's setup_warnings, allocation_warnings,
     cost_allocation_warnings and orphan_warnings are natural sources for findings[] and missing_data[].
 1.6 [PROPOSED] Two modes on one page, switched by the module's readiness flag. Not ready: SETUP mode (guide, explain
     fields, no analysis). Ready: ANALYSIS mode (explain verified outputs). The flags already exist: labour_ready on the
     Labour output contract, and model_ready / model_readiness_status on Cost Summary (the 2026-09-29 export read
     "blocked" with a reconciliation reason). This is the line between Section 4 and Section 5 without a new concept.
 1.7 [PROPOSED] One severity rule. "What deserves to interrupt an owner" (AI_STRATEGY G1 / D-C) is the severity threshold
     for findings[]. Define it once; Fin commentary, the 6.2 digest and any agent all use it. Month-end history (D-D)
     is the same decision as the snapshot design, so decide storage once.
 1.8 [PROPOSED] Action contract and approval, from the RACI plan. Actions: navigate_page, scroll_to_section, focus_field,
     set_field, highlight_metric, open_chart, focus_chart, focus_table, highlight_row, start_walkthrough. Flow: Fin
